# 역량맵 + 매일 AI 과제 루프 설계 — 2026-10-24

상태: **설계 초안 (사용자 검토 대기)**. 코드·DB·화면은 아직 변경하지 않았다. 이 문서가 확정되면 [금융권 백엔드 학습 설계 확정 기록](financial-backend-program-decisions.md)의 편성·시간·평가 정책 일부를 대체한다(§11).

**2026-10-24 사용자 결정: 기존 학습 기능·콘텐츠·문제·기록은 모두 초기화하고 새 루프로 다시 시작한다.** 보존·보관(`/archive`)은 하지 않는다. 범위와 절차는 §11.1이다.

## 1. 왜 다시 설계하는가

2026-09-27~10-24 실사용 기록과 원고를 대조한 결과다.

| 관찰 | 근거 | 원인 |
| --- | --- | --- |
| 수준이 너무 기초적 | 활성 과정 `JAVA-CORE-4W` 1일차가 `==`와 `equals` 비교 | 8년차 SI 개발자 기준이 아니라 일반 입문자 기준으로 편성 |
| 분량·깊이가 얕음 | "90분" 학습일 본문 약 1,600자 + 4줄 assert 예제. 1일차에 94자·117자 옛 원문 혼입, 동일 본문 3회 중복 배정 | 시간 표기와 실제 분량의 불일치, 원문 검수·배정 결함 |
| 이직 목표와 무관 | 금융권 백엔드 26주 설계는 `OUTLINE`/미리 보기 상태로 활성화되지 않음 | 목표에 맞는 과정이 사용 불가 |
| 형식이 안 맞음 | 완료 2일, 일일 확인 시험 응시 0회. 추가 학습은 10회 사용 | "읽고 완료" 동선은 손에 남는 결과물이 없음. 날짜 고정 편성이 밀리면 복구 수단이 없음(종료 예정 10-22가 지난 채 44개 미시작) |

결론: 원고를 고치는 것만으로는 해결되지 않는다. **"N일차 원고를 순서대로 읽는다"를 "목표 역량을 매일 한 번 직접 판단·답변하고 피드백을 받는다"로 바꾼다.**

## 2. 설계 원칙

1. **목표 기준**: 금융권 백엔드 이직 면접과 실무 판단에 필요한 역량만 다룬다. 이미 아는 기초는 과제에서 자연스럽게 통과되며 반복하지 않는다.
2. **출력 중심**: 매일 학습자가 직접 쓴다. 읽기 자료는 필요할 때 펼쳐 보는 참고이며 필수 단계가 아니다.
3. **하루 30~60분, 과제 1개**: 한 역량을 깊게 판단한다. 분량은 학습자 작성·피드백 시간을 포함해 산정한다.
4. **날짜에 묶지 않음**: 주간 목표 횟수만 둔다. 빠진 날은 쌓이지 않는다.
5. **결과물이 남음**: 답변·핵심 카드가 역량별 "면접 답변집"으로 누적된다.
6. **서버가 고르고 AI가 만든다**: 무엇을 할지는 서버가 DB 집계로 결정하고, AI에는 결정된 조건과 검수된 근거만 보낸다(§7, 9/27 데이터 경계 유지).
7. **추정은 추정으로 표시**: 역량 수준은 과제 결과로 추정한 값이며 숙달 증명으로 표현하지 않는다.
8. **돈은 금액으로 막고, 사용감은 막지 않는다**: 안전장치는 월 15,000원 하드 리밋 하나다(6개월 10만 원 예산, §7.2). 그 안에서는 AI 채점, 실시간 꼬리질문, 대화형 모의 면접을 횟수 걱정 없이 쓴다. 상한에 닿아도 루프는 자가 채점으로 끝까지 돈다.

### 3.1 수준 정의 (전 역량 공통)

| 수준 | 의미 | 면접에서 보이는 모습 |
| --- | --- | --- |
| 1 | 용어와 기본 동작을 설명한다 | 정의는 말하지만 상황에 적용하지 못함 |
| 2 | 주어진 상황에서 문제를 식별한다 | "여기서 lost update가 납니다"까지 |

| 4 | 여러 제약에서 설계하고 꼬리질문 2단계를 방어한다 | 운영·비용·장애 시나리오까지 판단 |

목표 수준은 P1=4, P2=3, P3=2를 기본으로 한다.

### 3.2 역량 시트 (근거 원문)

AI가 매일 다른 과제를 만들되 **정답 근거는 검수된 역량 시트로 고정**한다. 130일분 원고 대신 역량당 시트 1개(39개)만 작성·검수한다.

시트 구성: 핵심 개념(짧게) · 판단 기준 체크리스트 · 흔한 실수와 반례 · 수준별 기대 답변 요소 · 꼬리질문 후보 · 시나리오 재료(금융 도메인 상황 목록) · 공식 출처와 기준일 · 채점 검증용 기준 답안 3개(§6.3).

작성 흐름은 기존 [원문 저작 단계](financial-backend-program-decisions.md#ai-데이터와-생성-경계)를 따른다: 공식 자료 조사 → 작성 → 출처·기술 검수 → 발행. 사용자가 검수를 Claude에 위임했으므로(§12-4), Claude가 출처 대조와 기준 답안 검증(§6.3)을 마친 시트를 발행하고 `사용자 미검수`로 표시한다. 시트가 발행되지 않은 역량은 과제 선정에서 제외하고 화면에 "준비 중"으로 표시한다.

## 4. 하루 루프

### 4.1 과제 형식 3종

| 형식 | 학습자가 받는 것 | 학습자가 쓰는 것 |
| --- | --- | --- |
| `CASE` 장애·사례 분석 | 상황 설명 + 로그·지표·테이블 데이터·타임라인 | 원인 가설, 근거, 즉시 조치, 근본 수정안, 재발 방지 검증 |
| `REVIEW` 코드 리뷰·설계 판단 | Spring/SQL 코드 또는 설계안 2~3개 + 요구사항 | 문제점과 영향, 수정 방향, 선택 근거, 테스트할 경계 |
| `INTERVIEW` 면접 답변 | 면접 질문 (경력 질문은 승인된 경력 사실 기반) | 자유 서술 답변 → 꼬리질문 답변 |

| ① 브리핑 | 1분 | 오늘의 역량, 선정 이유("A3 마지막 점수 58점, 복습 시점 도래"), 현재 추정 수준 |
| ② 상황 읽기 | 5~8분 | 과제 자료. 역량 시트는 접어 둔 참고로 언제든 펼침 (펼친 여부 기록) |
| ③ 답 작성 | 15~20분 | 형식별 구조화 입력란. 자동 임시 저장 |
| ④ 피드백 | 5분 | 본 답 제출 즉시 AI 채점. 루브릭 항목별 점수, 놓친 점, 개선 답안, 모범 답 요소. 판단 불가는 `HOLD` |
| ⑤ 실시간 꼬리질문 | 5~10분 | AI가 **내 답을 보고** 가장 약한 지점을 파고드는 질문을 낸다. 답하면 짧은 피드백과 함께 다음 질문을 낸다(시간 모드별 최대 횟수). 면접관처럼 "왜 그 방법이죠?", "그 상태에서 서버가 죽으면요?"를 묻는다 |
| ⑥ 핵심 카드 | 3분 | 마지막 꼬리질문 응답에 포함된 카드 초안을 학습자가 고쳐 저장(3~5줄 요약 + 면접용 한 문장 + 복습 질문 1개, §4.6) |
| ⑦ 마무리 | 1분 | "오늘 과제가 도움이 됐나" 1~5점 + 선택 메모 |

시간 모드:
- **짧게 30분**: 꼬리질문 1회, 자료 분량 축소.
- **표준 45분**: 꼬리질문 2회. 기본값.
- **깊게 60분**: 꼬리질문 3회 + 제약 조건 1개 추가(난이도는 자동으로 올리지 않는다).
- 꼬리질문은 언제든 "여기까지"로 끝낼 수 있다. 끝내면 그때까지의 대화로 카드 초안을 만든다.

꼬리질문 점수는 본 답 점수에 ±15점 범위로 반영한다. 꼬리질문에서 근거를 보완하면 올라가고, 본 답의 근거가 무너지면 내려간다.

완료 조건은 ③ 제출 + ④ 피드백 확인이다. ⑤~⑦은 권장이며 건너뛸 수 있다. 점수는 다음 과제를 막지 않는다.

예산 상한에 닿은 달에는 ④가 자가 채점으로 바뀌고, ⑤는 과제 은행에 미리 저장된 꼬리질문 1~2개로 대체한다(§7.2).

### 4.3 시작 진단

긴 시험을 두지 않는다.

1. 영역별 자기 평가(5분): 10개 영역에 1~4 선택.
2. 첫 2주는 **탐색 모드**: 선정기가 P1 영역을 한 번씩 돌며 실제 수준을 측정한다. 자기 평가와 실측 차이를 화면에 보여준다.

### 4.4 주간 리듬

- **주간 목표**: 기본 주 4회(설정에서 2~7회). 연속 기록은 날짜가 아니라 "목표 달성 주" 단위로 센다.
- **주간 점검**(사용자가 정한 요일, 45~60분):
  - 이번 주 가장 낮았던 역량 2개에 새 시나리오로 재도전한다.
  - 20분 대화형 모의 면접(§4.5).
  - 주간 요약: 점수 변화, 새 카드, 다음 주 집중 역량.
- **한 과제 더**: 기존 추가 학습을 대체한다. 같은 루프를 하나 더 진행하며, 주간 목표 횟수에 포함된다. 하루 횟수 제한은 없다.
- **모의 면접 따로 하기**: 주간 점검과 별개로 언제든 시작할 수 있다.

### 4.5 대화형 모의 면접

- 면접관 AI가 한 턴씩 진행한다. 시작 전에 서버가 주제 질문 3개를 고른다: 약한 역량 2개 + 경력 질문(I1) 1개이며, 과제 은행의 `INTERVIEW` 과제에서 꺼낸다.
- 각 주제 질문마다 내 답을 듣고 꼬리질문을 최대 2회 이어 간다. 답이 충분하면 다음 주제로 넘어간다. 한 세션은 최대 9턴이다.
- 답은 텍스트로 쓴다. 음성 입력은 이번 범위에 넣지 않는다(§12-8).
- 진행 중에는 점수를 보여주지 않고 면접처럼 이어 간다. 끝나면 보고서 1회가 나온다: 질문별 평가, 가장 약했던 답, 다시 말한다면(개선 답안), 다음에 연습할 역량.
- 면접관 말투는 설정에서 고른다: 기본(차분), 압박형(반박·재질문이 많음).
- 모의 면접 결과도 해당 역량의 추정 수준 근거로 쓴다. 가중치는 일반 과제와 같다.

### 4.6 5분 카드 복습 (바쁜 날용)

30분을 낼 수 없는 날에도 끊기지 않게 하는 짧은 선택지다. AI 호출은 0회다.

1. 내가 저장한 핵심 카드 하나에서 복습 질문을 보여준다. 예: "재시도로 이중 출금이 나는 경로와 막는 방법을 설명해 보세요." 질문은 카드를 만들 때 카드 초안과 같은 응답에서 받아 둔다.
2. 머릿속으로 떠올리거나 짧게 적는다. 적는 것은 선택이다.
3. 카드를 펼쳐 비교하고 기억남 / 애매 / 모름 중 하나를 고른다.
4. 다음 복습일을 정한다: 모름이면 1일 뒤, 애매면 3일 뒤, 기억남이면 7 → 14 → 30일로 늘린다.

- 한 번에 1~5장을 연달아 할 수 있다.
- 주간 목표 횟수에는 넣지 않는다. 홈에는 "이번 주 카드 복습 N회"로 따로 보여준다.
- 결과는 역량 추정 수준에 반영하지 않는다. 다만 "모름"이 2번 연속 나온 카드의 역량은 선정기의 복습 계수를 1.5로 올린다.
- 홈은 오늘 과제를 시작하지 않은 채 학습 시작 시각에서 2시간이 지나면 "5분 복습만 할까요?"를 제안한다.

### 4.7 코딩 테스트 기록 (앱 밖 풀이)

직접 코드 작성 평가는 이 앱의 범위 밖이다(9/27 결정 유지). 그래도 금융권 채용에는 코딩 테스트가 있는 곳이 많으므로, 외부 사이트에서 푼 기록만 가볍게 남긴다.

- 입력 항목: 날짜, 사이트, 문제 이름과 링크, 유형(자료구조 / 탐색 / DP / 그리디 / 구현 / 기타), 결과(성공 / 실패 / 시간 초과 / 해설 참고), 소요 분, 메모.
- 화면에는 주간 풀이 수, 유형별 성공률, "해설 참고" 문제 목록(다시 풀 대상)을 보여준다.
- AI 호출과 외부 사이트 자동 수집은 하지 않는다. 링크는 저장만 한다.
- 역량 추정 수준(J1 포함)에는 반영하지 않는다. 앱의 분석형 평가로 코딩 테스트 구현 능력이 증명됐다고 표현하지 않는다는 9/27 원칙을 유지한다.
- 주간 점검 요약에 이번 주 풀이 수를 함께 보여준다.

### 4.8 이력서 검증 면접

면접관은 이력서와 자기소개서의 성과 문장을 가장 먼저 파고든다. 그래서 문장마다 압박형 면접 과제로 미리 검증한다.

1. **문장 등록**: 이력서·자기소개서의 성과 문장을 하나씩 붙여 넣고 관련 `career_fact`에 연결한다. 원본 파일은 올리지 않는다(§7).
2. **사전 점검 (AI 1회)**: 문장 하나에 대해 AI가 다음을 점검한다.
   - 수치와 단위가 서로 맞는가
   - 기술적으로 그럴듯한가(면접관이 의심할 지점)
   - 예상 꼬리질문 3~5개
   - 결과 상태: `수정 필요` / `근거 확인 필요` / `양호`
3. **압박형 면접 과제**: 그 문장을 주제로 `INTERVIEW` 과제를 만들고, 압박형 말투로 실시간 꼬리질문을 받는다(§4.2, §4.5).
4. **답변 정리**: 결과 카드에 "면접용 설명"과 "이력서 문장 수정안"을 함께 남긴다. 이력서를 실제로 고칠지는 사용자가 정한다.

- 선정기는 `수정 필요`·`근거 확인 필요` 문장을 I1 과제 후보로 우선한다. 문장마다 압박형 과제를 1회 이상 통과하면 `양호`로 바꿀 수 있다.
- 수치는 사용자가 "확인함"으로 표시하기 전에는 경력기술서 초안(§10.1)과 카드의 면접용 한 문장에 쓰지 않는다.
- **첫 검증 대상은 KDB 성능 개선 문장이다.** 2026-10-24 검토에서 두 가지를 확인했다.
  - "330ms(0.66초)"는 서로 다른 두 값이 한 문장에 함께 적혀 있다.
  - "인덱싱·페이징으로 3분까지 줄인 뒤 서비스 단 Buffered Stream 정렬로 더 빨라졌다"는 흐름은 "80만 건을 애플리케이션에서 정렬하는 게 왜 DB보다 빠른가"라는 질문을 거의 확실히 부른다. 측정 조건, 무엇을 전후로 비교했는지, 메모리 사용과 동시 사용자 영향을 설명할 수 있어야 한다.

## 5. 과제 선정 규칙 (서버)

후보는 시트가 발행된 역량이다. 각 후보 점수는 다음과 같다.

```text
점수 = 우선순위 가중치(P1=3, P2=2, P3=1)
     × 격차(목표 수준 − 추정 수준, 최소 0.5)
     × 복습 계수(복습 예정일이 지나면 1.5, 아직이면 0.6)
     − 다양성 감점(직전 2회와 같은 영역이면 −1, 같은 형식이면 −0.5)
```

- 복습 간격: 마지막 점수 60점 미만이면 2일, 60~79점이면 5일, 80점 이상이면 12일. 같은 역량에서 80점 이상이 연속되면 간격을 2배로 늘린다.
- 형식 배분: 주간 단위로 3형식이 각 1회 이상 나오게 한다. I 영역은 `INTERVIEW`, E 영역은 `CASE`를 우선한다.
- 난이도(3~5)는 추정 수준 + 1을 기본으로 한다. 직전 같은 역량 점수가 50점 미만이면 같은 난이도를 유지한다.
- 학습자는 오늘 과제를 "다른 역량으로 바꾸기"할 수 있다. 횟수 제한은 없다. 같은 역량을 3번 이상 바꾸면 홈에 "미루는 역량"으로 표시한다. 바꾼 이력은 선정에 반영한다.
- 선정 결과에는 근거 문장(`plan_reason`)을 함께 저장해 브리핑에 그대로 보여준다.

### 5.1 추정 수준 계산

- 해당 역량에서 채점된 최근 3개 과제의 점수를 난이도로 보정한 가중 평균을 쓴다(최근 과제일수록 가중치가 높다).
- 수준을 올리려면 근거 과제가 2개 이상 있어야 한다. 낮추는 데는 1개면 된다.
- `HOLD`, 건너뛴 단계, 시트를 펼친 과제는 점수를 그대로 쓰되 "참고하며 답함" 표시를 남긴다.
- 화면 표기는 "추정 수준 3 (근거 3개)"처럼 근거 수를 함께 보여준다.

## 6. AI 생성·채점

### 6.1 호출 단위

과제 자료는 **과제 은행**에 저장해 두고 재사용한다. 매번 새로 만드는 것은 내 답에 반응해야 하는 부분, 즉 채점·꼬리질문·면접관 턴뿐이다. 하루 횟수 제한은 두지 않고 월 예산(§7.2)만 지킨다.

| 작업 유형 (`ai_job.job_type`) | 언제 | 입력 | 출력 |
| --- | --- | --- | --- |
| `TASK_BANK_GENERATE` | 은행이 비었을 때. 한 호출에 과제 2~3개 | 역량 코드·시트 본문, 형식, 난이도, 변형 seed, (I1·I3·I4만) 확인된 경력 사실 | 과제 자료, 루브릭(합계 100), 모범 답 요소, 예비 꼬리질문 1~2개(예산 소진 시용) |
| `DAILY_TASK_GRADE` | 본 답 제출 시 | 본 답, 고정 루브릭, 시트의 해당 근거 부분 | `grading.schema.json` 형식 결과(새 프롬프트 폴더로 옮김, §6.5) + 첫 꼬리질문과 그 확인 포인트 |
| `DAILY_FOLLOWUP_TURN` | 꼬리질문 답마다 | 과제 자료 요약, 루브릭, **이 과제 안의** 본 답·이전 꼬리질문과 답 | 이번 답 피드백, 점수 보정, 다음 꼬리질문 또는 종료 + 카드 초안 |
| `MOCK_INTERVIEW_TURN` | 모의 면접 답마다 | 주제 질문 3개, 루브릭, **이 세션 안의** 대화 | 다음 면접관 발화(꼬리질문 / 다음 주제 / 종료) |
| `MOCK_INTERVIEW_REPORT` | 세션 종료 시 1회 | 세션 대화 전체, 루브릭 | 질문별 평가, 개선 답안, 추천 역량 |

- 꼬리질문과 면접관 턴의 확인 포인트는 서버에만 저장하며, 답하기 전에는 클라이언트에 보내지 않는다.
- 꼬리질문 횟수는 시간 모드가 정한다(§4.2). 면접 세션은 최대 9턴이다. 이 두 한도는 비용 때문이 아니라 학습 구조상의 길이다.
- 대화가 길어져도 입력이 무한정 늘지 않게 한다. 턴 입력에는 과제 자료 요약(최대 1.5k 토큰)과 이 과제·세션의 대화만 넣고, 대화가 6k 토큰을 넘으면 앞부분을 서버가 요약해 넣는다.
- 미리 생성(prefetch)은 하지 않는다. 대신 P1 역량 17개의 은행은 P2 끝에 한 번 일괄 생성해 두어서 처음 쓸 때 기다리지 않게 한다.
- 같은 과제를 다시 내는 경우는 60일이 지났고, 이전 점수가 80점 미만인 경우뿐이다. 이전 답안은 다시 쓴 뒤에만 비교용으로 보여준다.
- 과제는 시트 버전에 묶는다. 시트가 개정되면 해당 역량 은행의 미사용 과제는 사용 중지하고, 필요할 때 다시 생성한다.
- 과제 은행 생성은 급하지 않으므로 OpenAI Batch API(비동기 일괄 처리) 사용을 검토한다. 지원 여부와 할인 조건은 구현 시점의 공식 문서로 확인한다.

### 6.2 서버 검증 (생성 결과)

다음 중 하나라도 실패한 과제는 은행에 넣지 않는다. 재생성은 1회까지이며 그 비용도 예산에 포함한다. 재생성도 실패하면 `FAILED`로 끝낸다.

- 스키마를 따르는가.
- 루브릭 합계가 100인가.
- 정답 근거가 제공된 시트 항목 안에 있는가.
- 직접 코드 작성을 요구하지 않는가.
- 예상 소요 시간이 시간 모드 범위 안인가.
- 같은 역량의 최근 90일 과제와 지문 fingerprint가 겹치지 않는가.
- 사용 중지(`SUSPENDED`)되거나 폐기(`RETIRED`)된 과제와 지문이 겹치지 않는가(§6.4).

`FAILED`이면 은행에 남아 있는 다른 역량의 과제를 대신 보여준다.

### 6.3 채점 일관성 검증

같은 답에 매번 다른 점수가 나오면 추정 수준을 믿을 수 없다. 그래서 채점도 회귀 테스트한다.

- **기준 답안**: 시트마다 약함·보통·좋음 기준 답안 3개와 기대 점수 범위를 둔다(예: 약함 20~45, 보통 50~70, 좋음 80~100). 시트를 작성할 때 함께 쓰고 같이 검수한다.
- **저장 위치**: `content/competency-v1/calibration/<역량 코드>.json`. 사용자 답안이 아니라 작성한 예시이므로 저장소에 둔다.
- **언제 돌리나**: 채점 프롬프트, 모델, 루브릭 형식을 바꿀 때와 시트를 새로 발행하거나 개정할 때. 일상 실행은 하지 않는다.
- **통과 기준**:
  - 세 답안 모두 기대 범위 안에 든다.
  - 점수 순서가 약함 < 보통 < 좋음이다.
  - 같은 답안을 두 번 채점한 점수 차이가 10점 이내다.
- **실패하면**: 해당 변경을 반영하지 않는다. 시트 발행이었다면 발행을 보류한다.
- **비용**: 기준 답안 3개를 2번씩 채점해 시트당 6회 호출이다. 39개 전체로는 234회, 약 650원(§7.1 단가 기준)이다. 작업 유형 `CALIBRATION_GRADE`로 구분해 같은 월 예산에서 쓰고, 사용량 화면에도 따로 보여준다.
- **실행 방법**: 관리용 스크립트(`scripts/grading-calibration.ps1`)로 돌리고 결과를 `output/` 아래에 남긴다. `output/`은 추적 제외 폴더다.

### 6.4 과제 오류 신고

AI가 만든 과제나 피드백에는 기술 오류가 섞일 수 있다.

- 과제 자료, 피드백, 꼬리질문, 면접관 발화마다 **"이상해요"** 버튼을 둔다.
- 신고 사유: 사실 오류 / 채점 이상 / 문제가 모호함 / 시트 밖 내용 / 기타. 메모를 함께 쓸 수 있다.
- 신고하면 바로 일어나는 일:
  - 해당 은행 과제는 `SUSPENDED`가 되어 다시 선정되지 않는다(사용자가 한 명이므로 신고 1건이면 충분하다).
  - 그 과제 점수는 사용자가 "점수 빼기"를 고르면 추정 수준 계산에서 제외한다. 기본값은 유지다.
- 검토 결과:
  - 오류로 확인되면 은행 과제를 `RETIRED`로 바꾼다.
  - 원인이 시트에 있으면 시트 개정 대상으로 표시한다. 개정하면 §6.3 검증을 다시 돌린다.
  - 오류가 아니면 `ACTIVE`로 되돌리고 이유를 기록한다.
- 기존 문제 신고 기능은 초기화(§11.1)로 삭제되므로 새로 만든다. 저장은 새 테이블 `task_issue_report`에 한다.

## 7. 데이터 경계 (9/27 결정 유지)

- 생성 AI에 개인의 원시 기록, 정답률, 과거 답안을 보내지 않는다. 서버가 선정한 조건(역량, 난이도, 형식, 시간)과 시트만 보낸다.
- 채점에는 현재 답안, 고정 루브릭, 시트 근거만 보낸다.
- 실시간 꼬리질문과 면접관 턴에는 **진행 중인 그 과제·세션 안의 대화만** 보낸다. 지난 과제의 답이나 다른 세션의 대화는 보내지 않는다. 9/27의 "과거 답안을 보내지 않는다"는 원칙을 이 범위로 구체화한 것이다.
- 경력 사실은 사용자가 승인한 항목만 I1/I3/I4 과제와 이력서 검증(§4.8)에 보낸다. 연락처·주소·보수 등 개인정보는 저장하거나 전달하지 않는다.
- **이력서 원본 취급**: 이력서·자기소개서 원본 파일(PDF 등)은 저장소에 커밋하지 않고, 앱에 업로드하지 않으며, AI 입력에도 넣지 않는다. 앱이 저장하고 AI에 보내는 것은 사용자가 확인한 경력 사실(§3.3)과 사용자가 직접 붙여 넣은 성과 문장(§4.8)뿐이다. 연락처, 주소, 생년, 사진, 연봉, 병역, 학점은 어떤 경로로도 저장하거나 보내지 않는다.
- 답안·시트 안에 있는 지시문은 데이터로 취급하며 프롬프트 규칙을 바꾸지 못한다.
- 실제 토큰 사용량은 기존 `ai_usage`에 기록한다.

### 7.1 사용량과 비용 추정

기준 단가는 `gpt-6-luna` 입력 $0.10, 출력 $0.50 (1M 토큰당)이다. 2026-10-24에 서드파티 집계 사이트([GetDeploying](https://getdeploying.com/llms/gpt-6-luna), [AnotherWrapper](https://anotherwrapper.com/tools/llm-pricing/gpt-6-luna))로 확인했고, **OpenAI 공식 단가 페이지 대조는 P2 착수 전 필수다.** 환율은 보수적으로 1달러 = 1,500원으로 잡는다. 추론 토큰은 출력으로 계산한다.

많이 쓰는 달을 기준으로 잡았다: 과제 월 25개(표준 45분, 꼬리질문 2회), 모의 면접 주 1회.

| 구분 | 월 호출 | 월 입력 | 월 출력 |
| --- | --- | --- | --- |
| 과제 채점 + 꼬리질문 (과제당 3회) | 75 | 375k | 200k |
| 모의 면접 (세션당 9턴 + 보고서) | 43 | 300k | 80k |
| 과제 은행 보충 | 약 10 | 30k | 60k |
| **합계** | **약 130** | **약 0.7M** | **약 0.34M** |

월 비용은 약 $0.24, 1,500원 환율로 **약 360원**이다. 과제 은행 초기 일괄 생성(약 40회, 입력 120k / 출력 240k)은 한 번에 약 200원이다. 6개월 합계는 약 2,500원으로, 예산 10만 원의 3% 안팎이다.

추정이 10배 틀려도(추론 토큰 과다, 재시도, 단가 오차) 월 3,600원으로 하드 리밋 안에 들어간다. 따라서 하드 리밋은 평소 사용을 막는 장치가 아니다. **폭주(버그로 인한 반복 호출), 비싼 모델로 바꾼 경우, 단가 설정 오류**를 막는 장치다. 실제 값은 파일럿(§10 P4)에서 `ai_usage`로 측정해 이 표를 갱신한다.

### 7.2 비용 상한

9/27 결정의 "금액 차단은 필수 요구가 아니다"를 이 설계에서는 **대체**한다.

- **월 하드 리밋 15,000원**: 6개월이면 9만 원으로, OpenAI 쪽에 설정한 6개월 10만 원 한도보다 먼저 걸린다. 기존 `ai_budget`(`limit_amount`, `hard_limit_enabled`)에 달력 월 단위 행을 둔다. 설정 화면에서 금액을 낮출 수 있고, 올릴 때는 6개월 누적이 10만 원을 넘지 않는지 경고한다.
- **호출 전 예약**: 호출마다 최대 비용을 `ai_job.reserved_amount`에 먼저 예약한다. 계산식은 (예상 입력 토큰 × 입력 단가 + `max_output_tokens` × 출력 단가) × 환율이다. 남은 예산이 예약액보다 적으면 호출을 보내지 않는다. 호출 뒤에는 실제 사용량으로 정산하고 남은 예약을 푼다.
- **단가를 모르면 호출하지 않는다**: 모델 단가 설정이 없거나 만료되면 AI 호출을 막는다(fail closed). 화면에는 "비용 계산 불가로 AI 기능 중지" 사유를 보여준다.
- **폭주 방지**: 사용자별 동시 AI 작업 1개(기존 보호 유지), 하루 AI 호출 60회. 하루 60회는 정상 사용(하루 과제 5개 + 모의 면접 2회 ≈ 35회)으로는 닿지 않는 값이다.
- **토큰 상한**: 작업 유형별 `max_output_tokens`를 고정한다. 추론 토큰을 포함한 값으로, 채점·꼬리질문 4k, 면접관 턴 3k, 보고서 5k, 은행 생성 10k다. 평균 사용량(§7.1)보다 넉넉하게 잡아 답이 잘리지 않게 하고, 예약 금액은 이 상한으로 계산한다.
- **알림**: 월 예산의 50%와 80%에서 알림 센터로 한 번씩 알린다. 평소 사용으로는 오지 않을 알림이라, 오면 이상 징후로 본다.
- **상한에 닿았을 때**: 루프는 멈추지 않고 다음 달 1일까지 아래처럼 진행한다.
  - 과제 채점은 자가 채점으로 한다. 루브릭 체크리스트와 모범 답 요소를 보고 학습자가 충족한 항목을 체크하면 서버가 점수를 계산한다. 이 점수는 추정 수준에 가중치 0.7로 반영하고 "자가 채점"으로 표시한다.
  - 꼬리질문은 은행의 예비 꼬리질문으로 대체한다.
  - 모의 면접은 쉰다.
  - 화면에 사유와 재개 날짜를 보여준다.

### 7.3 비용 기록 연결 (현재 결함 보완)

2026-10-24 점검 결과, 지금은 앱이 비용을 계산하지 못한다.

- `ai_usage`의 `pricing_snapshot`이 `{}`이고 `provider_cost_usd`와 `budget_cost_amount`가 비어 있다(호출 14건 전부).
- `ai_budget`에는 하루 단위 기간에 `limit_amount = 0`인 행만 있다.
- 따라서 지금 실제로 작동하는 금액 안전장치는 OpenAI 쪽 한도뿐이다.

P2 필수 작업:

1. **단가 설정**: 모델별 입력·캐시 입력·출력 단가(USD/1M), 적용 시작일, 출처 URL, 확인일을 저장한다(`ai_model_price` 테이블). 공식 단가를 확인한 값만 넣는다.
2. **환율**: 설정값으로 둔다(기본 1,500원, 보수적). 호출마다 `ai_usage.fx_rate`에 기록한다.
3. **호출마다 기록**: `pricing_snapshot`(적용 단가·환율·계산식 버전), `provider_cost_usd`, `budget_cost_amount`를 기록한다. 추론 토큰과 캐시 입력은 공식 과금 규칙대로 반영한다.
4. **예산 기간**: 달력 월 단위 `ai_budget` 행을 자동으로 만든다. 기존 하루 단위 행은 이력으로 남기고 판정에는 쓰지 않는다.
5. **사용량 화면**: 설정에서 이번 달 사용액·상한·남은 금액, 6개월 누적, 작업 유형별 호출 수와 비용, 최근 호출 내역을 보여준다.
6. **대조**: 매달 OpenAI 사용량 대시보드와 앱 합계를 사용자가 비교하고 `ai_usage.reconciled_at`에 표시한다. 차이가 10%를 넘으면 단가나 환율 설정을 고친다.
7. **테스트**: 예약 → 정산, 상한 직전 호출 차단, 단가 없음 차단, 동시 요청 시 이중 예약 방지, 월 경계를 PostgreSQL IT로 검증한다.

### 10.1 경력기술서 초안 내보내기 (P5)

I1 경력 카드는 결국 경력기술서 문장이 된다.

### 11.1 초기화 범위와 절차 (R0)

**절차** (순서를 지킨다)

1. **현재 상태를 커밋한다.** 옛 학습 코드 대부분이 아직 커밋되지 않았다(2026-10-24 기준 380개 파일 변경). 이 상태에서 지우면 git 이력으로도 되돌릴 수 없다. 커밋한 뒤 그 커밋에 `legacy-before-reset` 태그를 단다.
2. **DB를 백업한다.** 기존 `scripts/database-backup.ps1`를 쓰고, 복원 리허설(`scripts/database-restore-drill.ps1`)로 백업이 열리는지 확인한다.
3. **데이터를 삭제한다.** 아래 "삭제" 테이블을 한 트랜잭션에서 비운다. 실행 전에 테이블별 행 수를 기록하고, 실행 후 0인지 확인한다.
4. **옛 코드·화면·콘텐츠를 삭제한다.** Backend의 학습·시험·문제·진척·대시보드·AI 연습 모듈, Frontend의 해당 화면, `content/` 원고, `prompts/financial-backend-v1/`를 지운다. 남는 기능(로그인·설정·알림·연동)이 참조하던 부분은 끊는다.
5. **테이블을 삭제한다.** 새 migration(V34)으로 옛 학습 테이블을 DROP한다. 기존 migration 파일은 수정하지 않는다. 옛 테이블을 검사하던 테스트(`BusinessSchemaIT` 등)는 새 기준으로 고친다.
6. **확인한다.** Backend·Frontend 빌드와 테스트, Compose 실행, 로그인·설정·알림·연동 화면이 열리는지 확인한다.

| 설정 | `user_setting` | 새 컬럼만 추가(§8) |
| 연동 연결 | `integration_connection`, `notion_credential`, `notion_oauth_state`, `notion_revocation`, `browser_connection`, `browser_oauth_state`, `push_subscription`, `notification_preference`, `sync_job`, `sync_attempt`, `integration_mapping` | 다시 연결하는 수고를 줄인다. 쓰지 않게 된 연결은 설정에서 해제 |
| AI 비용 기록 | `ai_job`(23), `ai_usage`(14), `ai_budget`(6) | 비용 이력. `ai_job`의 옛 입력 스냅샷은 비운다(`input_snapshot`, `result_payload`를 NULL로) |
| 기타 | `audit_event` | 감사 기록 |

QA용 Compose 환경(`compose.course-qa.yaml`, `compose.extra-learning-qa.yaml`, `compose.study-program-qa.yaml`)은 옛 학습 기능 검증용이다. R0에서 compose 파일과 해당 Docker volume을 함께 지운다(§12-11 결정됨). volume은 지우기 전에 `docker volume ls`로 이름을 확인하고 기록한다.
