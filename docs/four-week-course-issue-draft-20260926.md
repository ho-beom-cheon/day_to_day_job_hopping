# 이슈 초안: 4주 핵심 역량 과정과 검수·적재·발행 체계

상태: 사용자 승인으로 [이슈 #9](https://github.com/ho-beom-cheon/day_to_day_job_hopping/issues/9) 등록 완료. 구현·검증 및 기존 공개 서버 발행 완료. 상세 근거는 `content/java-four-week-v1/review.md`와 `docs/site-completion-stages-20260926.md`를 참조한다.

## 문제와 분석

- 현재 발행 DB에는 6학습일, 본문 6개, 기본 문제 6개, 시험 4개가 있다.
- `content/operational-v1`에는 26주 목차와 1주차 편집 초안만 있다. 운영 발행된 원고가 아니다.
- 기존 이슈 #5는 운영 콘텐츠 제작을 명시적으로 제외한다. #8은 API·외부 연동·QA·운영 범위다. 2026-09-26 원격 이슈 1~8을 조회했으며 이번 콘텐츠 범위에 맞는 이슈가 없다.
- `LearningCatalog`는 기간 6개월과 월 모듈 6개를 강제한다. `LearningCommandService`는 목표 종료일을 시작일+6개월-1일로 계산하고, OpenAPI도 같은 의미를 명시한다. 4주 원고를 그대로 발행할 수 없다.
- 발행된 과정과 이미 배정된 기록은 불변이다. 새 과정 버전으로 제공해야 한다.

## 제안 범위

### 1. 4주 독립 과정 지원

- 중립적인 이름 `핵심 역량 학습 과정 · Java 4주`로 새 템플릿을 만든다.
- 교육 기간은 1개월, 교육 주차 4개, 학습일 20개다. 실제 달력 일정은 기존 시작일·휴식일 정책으로 배정한다.
- 기존 6개월 과정의 공개 응답과 목표일은 그대로 유지한다. 신규 과정에 한해 기간 값을 사용하도록 카탈로그 검증·배정·온보딩·로드맵 안내를 정렬한다.
- 별도 계약 정렬 문서에서 목표 종료일 의미와 기간 범위를 명시한다. 원본 설계 패키지를 몰래 수정하지 않는다.

### 2. 학습·평가 콘텐츠

- 1주: 값과 동등성. 2주: 컬렉션과 제네릭. 3주: 오류와 테스트. 4주: 동시성과 JVM.
- 각 학습일: 목표, 자체 설명, 코드 예제, 실습 과제, 수락 기준, 확인 문제, 정답·해설, 공식 출처.
- 확인 문제는 하루 10문항을 초기 편집 목표로 하되 단순 반복이나 분량 채우기 문항을 넣지 않는다.
- 일간 시험 20개, 주간 시험 4개, 월간·최종 시험 각 1개를 편성한다. 시험 문항 수·배점·시간은 별도 정책 파일에서 검토하고 하루 90~120분 계획과 대조한다.
- 실습 과제와 수락 기준은 학습 본문에 포함한다. 검토자 가이드는 학습 화면에 노출하지 않는다.
- 구조 검사와 기술 검수, 실행 가능한 예제 테스트를 통과한 자료를 발행 대상으로 지정한다. 작성 완료와 운영 발행 완료를 구분한다.

### 3. 적재·검증·발행

- 명시적인 운영자 도구로 버전이 있는 원고를 DRAFT에 적재한다. 서버 기동 시 자동 seed하지 않는다.
- 외부 ID와 콘텐츠 digest로 같은 원고의 중복 적재를 차단하고 변경은 새 버전으로 처리한다.
- 64비트 DB ID를 문자열로 다룬다. 오류가 나면 적재 트랜잭션 전체를 취소한다.
- 콘텐츠·문제·시험 참조, 정답, 순서, 분모, 교육 주차·기간을 확인한 뒤 기존 카탈로그 발행 흐름을 사용한다.
- 새 과정 공개 후 첫 화면의 제공 범위를 함께 갱신한다. 기존 사용자 과정을 자동 재배정하지 않는다.
