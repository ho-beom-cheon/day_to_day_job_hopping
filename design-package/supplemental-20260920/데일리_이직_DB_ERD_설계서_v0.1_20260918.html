1. 목적과 산출물

이 설계는 매일의 학습, 문제 풀이, 오답 복습, 시험, 월말 평가, 휴식일 조정, AI 사용량, 웹 푸시 및 Notion/Slack 연동을 저장할 구조를 정의한다. 학습을 저장했는데 외부 연동 실패로 함께 취소되거나, 문제 수정으로 과거 성적이 바뀌거나, 휴식일 이동으로 완료 이력이 사라지는 것을 막는 것이 핵심이다.

전체는 업무·운영 테이블 46개다. 로그인 세션에 필요한 SPRING_SESSION, SPRING_SESSION_ATTRIBUTES 2개는 Spring Session JDBC의 선택 버전용 PostgreSQL 공식 스키마를 별도 마이그레이션으로 반영한다. 이 두 테이블은 업무 DDL 46개에 포함하지 않는다. 프레임워크가 만드는 Flyway 이력 테이블 역시 별도다. [S3]

테이블 수는 서버·서비스 수가 아니다. 초기에는 Spring Boot 단일 애플리케이션과 PostgreSQL 단일 DB 안에서 관리하고, 별도 마이크로서비스나 메시지 브로커를 필수 전제로 추가하지 않는다.

4. 공통 물리 설계

4.1 스키마·명명·식별자

업무 스키마는 daily_career, 테이블과 컬럼은 영문 단수 snake_case, 기본키는 id, 참조는 <대상>_id를 사용한다. 자바 엔티티와 API 필드는 별도 매핑한다. DB revision과 콘텐츠 version_no, 일정 schedule_revision, 채점 run_no, 보고서 report_version은 의미가 다르므로 합치지 않는다.

내부 기본키는 bigint GENERATED ALWAYS AS IDENTITY, 관계키는 같은 bigint다. 외부 API에서 무작위 UUID로 임의 변경하지 않는다. 다만 PostgreSQL bigint의 범위와 웹 클라이언트의 안전한 정수 표현 범위가 다르므로, API에서 ID를 문자열로 통일하는 보완안을 제시한다. 기존 API Long 예시가 실제 JSON 숫자 계약이라면 API 명세·OpenAPI·TypeScript 타입을 함께 변경해야 한다. v0.1에서는 이 결정을 완료한 것으로 간주하지 않는다. [S6, S7]

식별자를 어렵게 추측하도록 만드는 것과 접근 권한은 별개다. 모든 개인 데이터 읽기·변경은 인증된 사용자 소유권을 검사한다.

timestamptz는 입력한 Asia/Seoul 이름을 보존하는 자료형이 아니다. 순간과 별개로 과정·설정의 시간대 이름을 저장한다. 과거 학습 날짜는 사용자 설정 변경으로 이동시키지 않는다. [S2]

JSONB에 사용자 목록·관계 ID 배열·학습 상태 전체를 몰아넣지 않는다. 시험 지문과 보기처럼 불변 문서에 속하는 구조는 JSON으로 보관할 수 있지만, 사용자·과정·문제·응시·노트 관계는 FK로 둔다.

4.3 공통 컬럼과 동시성

변경 가능한 행에는 created_at, updated_at, revision을 둔다. updated_at DEFAULT now()는 INSERT 기본값일 뿐, UPDATE 때 자동으로 바뀌지 않는다. JPA 또는 직접 SQL 갱신 코드가 시각과 revision을 함께 갱신한다. DB 자동 증가 트리거와 JPA 버전 갱신을 중복 적용하지 않는다.

제출 기록, 원천 점수, 일정 변경 감사 등 역사 데이터는 신규 행 추가가 기본이다. created_at만 있는 테이블도 읽기 전용 자동 보장을 받는 것은 아니다. 운영 역할의 권한 및 서비스 경로로 UPDATE/DELETE를 막고, 보존 종료 배치는 별도 권한으로 수행한다.

4.4 키와 인덱스

사용자 소유 테이블에는 (id,user_id) 유니크를 두고, 자식 테이블은 가능하면 (부모_id,user_id) 복합 FK를 사용한다. 다른 사용자의 시험·노트·AI 작업을 연결하는 실수를 DB 수준에서 줄인다. 개인 과정의 날짜·배정 항목은 과정 ID까지 묶어 같은 과정임을 확인한다.

다만 공유/개인 콘텐츠를 함께 참조하는 권한, 같은 사용자 안의 추가 의미 일치, 트리 깊이와 기간 겹침은 이러한 FK만으로 해결되지 않는다. 서비스 검증 목록을 별도로 적용한다.

PostgreSQL은 PK/유니크를 위한 인덱스를 만들지만 참조하는 FK 컬럼의 인덱스는 자동 생성하지 않는다. 초안은 FK 및 대표 조회의 인덱스 후보를 포함한다. 모두 영구 유지하라는 뜻은 아니며 실제 실행계획·쓰기 비용을 보고 정리한다. [S4]

4.5 참조 삭제

업무 FK는 기본 ON DELETE RESTRICT다. 문제나 사용자를 삭제하면서 시험·오답·성적이 연쇄 삭제되지 않게 한다. 탈퇴 시 서비스 이용을 중지하고 세션·외부 비밀·대기 작업을 정리하되, 실제 데이터 삭제·익명화와 백업 보존은 별도 승인 정책에 맞춘 명시적 배치로 처리한다. 승인된 삭제 작업은 자식부터 순서를 정해 실행한다.

월말 평가와 outbox의 일부 관계는 집계·이벤트 관계이지 단일 직접 FK가 아니다. 개념 흐름의 연결선을 모두 FK로 오해하지 않는다. HTML의 영역별 구조도는 핵심 관계를 표시하는 탐색용이고, 모든 컬럼·FK의 기준은 사전과 .mmd다.

6. 학습·휴식일 규칙

6.1 교육 차수와 달력 날짜를 분리

커리큘럼의 1개월차/1주차/1일차는 교육 순서다. learning_day.local_date는 실제 날짜다. 사용자가 특정 금요일을 휴식일로 바꾸어도 교육 내용·문제 버전·완료 기록의 식별자가 바뀌어서는 안 된다.

learning_day_item은 배정 작업의 안정적인 식별자이고, 실제 학습 시간은 learning_session에 기록한다. 같은 항목을 여러 번 열어도 항목은 하나이고 세션은 여러 개일 수 있다.

6.2 정책과 날짜별 예외

schedule_policy는 주당 휴식 횟수·학습 시간·유효 기간을, schedule_rest_weekday는 요일을 저장한다. 완전한 주의 기본 정책에서는 요일 행 수가 weekly_rest_count와 같아야 한다. 시작/종료의 부분 주, 날짜별 휴식 예외는 달력 생성 규칙으로 처리한다.

매주 수·일요일을 쉬고 싶으면 수=3, 일=7 두 행을 저장한다. 특정 주 금요일만 추가로 쉬는 요청은 learning_day.source=MANUAL, day_type=REST로 표시하고 원래 정책을 모두 덮어쓰지 않는다. 휴식일 7일 설정은 학습 가능한 날이 없어지는 상태이므로 과정 일시중지와 배정 보류로 처리하며, 무한한 재배치를 시도하지 않는다.

정책 범위는 [effective_from,effective_to)이고 같은 과정에서 겹치면 안 된다. 행 사이 개수·기간 겹침은 단순 CHECK가 아니라 과정 행 잠금과 서비스 검증으로 처리한다. [S4, S5]

6.3 재배치

오늘의 미시작 항목과 미래 일정만 변경한다. 이미 시작·완료한 항목을 휴식일로 숨기지 않는다. 과거 일정은 유지하며 늦게 공부한 사실은 실제 세션 및 완료 시각으로 남긴다. 지난 미이행 항목은 오늘 화면의 보충 학습에 노출할 수 있지만 원래 마감 날짜를 삭제하지 않는다.

미래 항목 이동은 과정 행을 잠그고 expectedScheduleRevision을 검사한 한 트랜잭션에서 처리한다. 일정 정책·날짜·항목 배정·예상 종료일을 변경하고, schedule_change와 outbox를 함께 저장한다. 이전 계획 기반 알림은 취소하고 새 계획의 알림 키를 새로 산정한다.

기본 정책은 미시작 학습량을 남은 날짜에 압축하지 않고 예상 종료일을 연장한다. 종료일 고정 모드는 학습량 상한·사용자 동의 규칙이 있어야 하며, 이 규칙이 승인되기 전 기본 구현에서 활성화하지 않는다.

6.4 학습 완료와 시간

개념은 명시적인 완료 처리, 문제·면접·시험 활동은 필수 답안 제출을 학습 수행 완료의 기본으로 제안한다. 높은 점수를 받아야만 완료로 인정하는 규칙과 AI 채점 완료 여부는 별도다. 화면을 열기만 해서는 완료되지 않는다.

학습 시간은 서버 수신 시각·heartbeat 순번으로 검증한다. 같은 순번의 재전송을 중복 합산하지 않고 장시간 비활성 구간은 제외한다. 구체적인 heartbeat 간격·idle 기준은 구현 정책으로 확정한다. 자정을 넘는 활동은 과정 타임존의 날짜 경계에서 세션을 분할한다.

7. 문제·시험·채점

7.1 원형과 버전

problem은 동일한 개념의 문제 식별자, problem_version은 실제 지문·보기·정답·해설·채점 규칙의 고정 버전이다. test_version은 출제 구성·시간·합격 규칙을 고정한다. 발행 후 본문 수정은 새 버전으로 한다.

개인 AI 생성 문제는 owner_user_id로 접근을 제한한다. answer_key, rubric, grading_snapshot은 서버 전용 필드다. 엔티티를 그대로 API 응답으로 직렬화하지 않고 공개 DTO와 채점 DTO를 분리한다.

7.2 개별 풀이와 시험 답안

개별 연습은 problem_attempt가 한 번의 답안을 저장한다. 시험은 test_attempt와 test_attempt_item이 응시 전체와 문항별 답안을 저장한다. 둘은 채점 실행/결과 구조를 공유하지만 원천 답안을 하나의 모호한 범용 JSON 테이블에 섞지 않는다.

기존 PUT /test-attempts/{attemptId}/answers/{problemId}를 유지하려면 problemId를 문제 원형 ID로 명확히 정의한다. 서버는 응시에 속한 시험 버전과 test_item.problem_id로 단일 문항을 찾는다. (test_version_id,problem_id) 유니크가 이를 보장한다. 문항 중복 출제를 허용하도록 정책을 바꾸면 API 경로 역시 attemptItemId 등으로 바꿔야 한다.

7.3 자동 저장과 제출 경합

답안 저장과 제출은 모두 같은 test_attempt 행을 먼저 잠근다. 답안 저장 시 응시 상태·서버 마감·답안 revision을 확인하고, 문항 답안과 응시 revision을 같이 증가시킨다. 제출은 최종 응시 revision을 검사해 누락된 저장과 충돌을 발견한다.

제출 트랜잭션은 중복 방지 레코드 획득 → 응시 잠금 → 소유권/마감/최종 revision 검증 → 제출 시각·답안 해시 확정 → 채점 실행과 outbox 생성 → 응답 확정 순서다. 외부 AI 호출은 이 트랜잭션 안에서 하지 않는다. 행 잠금은 트랜잭션 동안 다른 갱신과의 충돌을 직렬화하는 수단이다. [S5]

제출 후 늦게 도착한 자동 저장은 거부한다. 같은 제출 요청 재전송은 최초 제출 결과를 반환한다. 제출이 성공했으나 채점이 실패한 경우에는 답안을 보존하고 채점만 재시도한다. 시간 초과 제출과 사용자 제출도 같은 잠금 경로를 사용한다.

7.4 채점과 재채점

grading_run은 개별 풀이 또는 시험 중 정확히 하나를 대상으로 한다. grading_result는 개별 답안 또는 해당 시험의 문항과 연결된다. 복합 FK는 채점 실행과 시험 문항의 응시 소속을 맞춘다.

획득 점수와 만점 범위는 CHECK로 제한한다. 원본 배점과 결과 만점의 일치, 모든 문항 결과 존재, 루브릭 합계 일치는 서비스에서 검사한다. 성공한 run만 현재 공식 성적으로 지정하고, 재채점은 새로운 run을 만들어 완료한 뒤 공식 포인터를 교체한다. 공식 run 유니크는 개별 풀이와 시험 각각 적용한다.

AI 평가 점수를 절대적인 숙련도 사실처럼 표시하지 않는다. 규칙 버전·평가 방식·근거·표본 수를 함께 보관하고, 재평가 가능성을 유지한다.

8. 오답·복습·면접

wrong_answer는 사용자·문제 원형당 하나의 노트다. 오답을 낸 시점마다 wrong_answer_occurrence를 추가하며 실제 채점 결과를 참조한다. 이 구조로 같은 문제를 다시 틀려도 노트가 계속 복제되지 않으면서 시도 이력은 남는다.

서술형/면접은 단순 정오 대신 점수·평가 기준에 따른 복습 필요 여부를 정책으로 판정한다. 그 기준은 grading_rule_version과 연결해 일관되게 적용한다. 재채점으로 기존 오답 판단이 사라지면 발생 건을 INVALIDATED로 두고 노트 상태·미래 복습을 재계산한다. 사용자가 쓴 노트를 자동 삭제하지 않는다.

review_task는 복습 예정과 완료를 기록한다. 완료 후 다음 회차는 새 행으로 생성한다. 해당 노트에 살아 있는 예약은 하나만 두며, 복습 완료 풀이가 같은 사용자·문제인지 서비스가 검증한다. 휴식일에 복습을 미룰지 발송만 막을지는 알림 정책과 복습 정책을 구분해 처리한다.

면접 질문은 question_type=INTERVIEW, 꼬리질문은 problem.parent_problem_id로 연결한다. 대화 자체는 AI 대화/메시지에, 평가할 실제 답변은 개별 문제 풀이와 채점 결과에 남긴다.

9. 진척도와 월말 평가

9.1 일정 이행률

분모는 조회 대상 기간에서 지역 날짜가 이미 끝난 학습일 중 필수 배정 항목이 존재하는 날짜 수다. 휴식일·미래 날짜·아직 진행 중인 오늘은 제외하고 오늘의 현황은 별도로 표시한다. 분자는 해당 날짜의 마감까지 모든 필수 항목을 완료한 날짜 수다.

늦게 완료하면 커리큘럼 완료율은 올라가지만 과거의 기한 내 이행률이 소급 상승하지 않는다. 과거 일정 변경을 금지하는 이유도 이 지표의 의미를 보존하기 위해서다. 분모 0이면 100%가 아니라 null과 “아직 평가할 학습일이 없어요”로 표시한다.

9.2 커리큘럼 완료율

분모는 등록한 고정 커리큘럼 버전의 필수 ITEM 가중치 합이다. 아직 개인 일정으로 생성하지 않은 미래 항목도 포함한다. 분자는 해당 원본 ITEM에 연결된 완료 배정 항목의 가중치 합이다. 동일 원본은 한 번만 계산한다.

보충·반복 문제 풀이 횟수, 학습 세션 수, 선택 학습은 분모와 분자를 임의로 늘리지 않는다. 휴식일을 늘려도 분모는 변하지 않는다. 분모 0인 잘못된 커리큘럼은 발행 단계에서 거부한다.

9.3 숙련도

분야별 현재 공식 채점 결과를 근거로 계산한다. 연습을 무한 반복해 점수가 편향되지 않게 집계 기간·문제별 대표 시도·시험/연습 가중치를 calculation_version 정책에 명시한다. v0.1에서는 미승인 가중치를 임의로 확정하지 않는다. 점수뿐 아니라 표본 수·최근 평가일·평가 유형을 보여준다.

원천에는 실제 답안·배점·획득 점수·문제 분야를 남긴다. 초기 대시보드 집계는 SQL 조회로 제공하고, 성능 문제가 확인되기 전 별도 진척도 원본 테이블이나 복잡한 이벤트 소싱을 도입하지 않는다.

9.4 월말 보고서

월말 평가는 month_start가 가리키는 달력 월과 과정 기간의 교집합을 평가하는 제안이다. 6개월 과정이 중간 날짜에 시작하면 부분 월을 포함해 7개 달력 월에 걸칠 수 있으므로 보고서 개수를 무조건 6개로 제한하지 않는다. 교육 1개월차와 달력 9월을 화면에서 구분한다.

원천 집계는 일관된 DB 스냅샷에서 계산하고 분자·분모·문제/채점 버전·대상 기간·규칙 버전을 metrics_snapshot에 저장한다. 단지 created_at <= cutoff 조건만으로 과거 상태를 재현할 수 있다고 가정하지 않는다. AI 보고서는 이 고정 입력을 받아 생성한다. 이후 재채점이나 늦은 학습이 생기더라도 발행된 보고서는 덮어쓰지 않고 필요한 경우 새 버전을 만든다.

10. AI 작업·사용량·예산

AI는 ai_job이라는 논리 작업과 ai_usage라는 실제 호출을 나누어 기록한다. 한 작업이 네트워크 문제로 두 번 호출됐다면 실제 사용량도 최대 두 건 발생할 수 있다. API 요청 멱등성만으로 외부 제공자의 과금까지 정확히 한 번이라고 보장하지 않는다.

예산 행을 잠그고 이미 확정된 비용 + 아직 정산하지 않은 예약액 + 새 요청 예약액을 검사한다. 허용된 요청만 예약액을 확보하고 작업을 생성한다. 실제 호출 전에 필요한 비용 상한을 정할 수 없는 작업은 엄격한 한도 보장의 대상이 될 수 없으므로 출력 한도·안전 여유·요청 거부 기준을 구현 정책으로 둔다.

호출 이후 단가·환율·모델·프롬프트 버전과 사용량을 기록해 예산 통화로 정산한다. 캐시 입력은 전체 입력의 일부, 추론 출력은 전체 출력의 일부로 모델링하므로 전체 토큰에 다시 더하지 않는다. 모델별 제공 필드가 다르면 어댑터가 정규화한다.

제공자가 처리했는지 알 수 없는 시간 초과는 UNKNOWN으로 남기고 비용을 0으로 처리하지 않는다. 자동 재호출 전에 조회·추적 ID·예약액·재시도 허용 여부를 확인한다. 사용량을 끝내 확인하지 못한 경우의 보수적 정산 정책도 별도 승인한다.

API 키·Google 로그인 토큰·Notion 토큰·Slack Webhook URL을 AI 입력, 작업 결과, 오류 메시지, 감사 로그에 저장하지 않는다.

11. 알림·Notion·Slack

11.1 로컬 저장을 먼저 확정

학습 완료 트랜잭션에는 학습 결과와 outbox 이벤트만 원자적으로 기록한다. outbox 작업자가 알림·AI·동기화 작업을 등록한다. 외부 오류가 나더라도 이미 성공한 학습 저장은 되돌리지 않는다. 반대로 업무 트랜잭션이 롤백되면 outbox도 남지 않아야 한다.

작업 큐의 기본 보장은 최소 1회 처리다. 중복 작업 등록은 각 목적의 업무 키/유니크로 막고, 외부 효과까지 정확히 한 번이라고 표현하지 않는다. lease_token, lease_until로 점유와 복구를 관리하며, 만료 후 돌아온 이전 작업자는 자신의 토큰이 유효할 때만 결과를 반영한다.

11.2 알림

앱 알림 본문 1개에 웹 푸시 기기별/Slack 채널별 전송이 붙는다. 모바일 두 기기와 PC 한 기기가 있다면 동일한 알림에 여러 전송 행이 생길 수 있다. 읽음 상태와 제공자의 전송 수락 상태는 별개다.

휴식일 리마인드·방해 금지 시간·일정 변경 취소를 발송 직전에 재검증한다. 초기 스키마는 PWA 웹 푸시 기준이다. 향후 네이티브 앱 출시를 승인하면 FCM/APNs 토큰 테이블 및 갱신 정책을 추가한다.

11.3 Notion 단방향 동기화

연결 자격증명은 integration_connection.credential_ref, 객체 대응은 integration_mapping, 논리 작업은 sync_job, 매번의 통신 결과는 sync_attempt에 둔다. 앱 원본 행의 revision과 외부에 보낼 문서 버전은 다를 수 있으므로 전송용 local_revision을 따로 증가시킨다.

단일 매핑은 한 작업자가 순서대로 처리한다. 오래된 작업이 최신 페이지를 다시 과거 상태로 덮어쓰지 않도록 성공 버전을 확인하고 구버전은 SUPERSEDED 처리한다. 원격 API에는 일반적인 로컬 DB 트랜잭션 보장이 없으므로 원격 생성 성공 직후 응답이 끊기는 경우는 안정적인 앱 source key로 이미 생성된 객체를 확인해야 한다. 미확인 상태에서 새 페이지 생성을 무조건 반복하지 않는다.

Notion은 앱 관리 속성·블록과 사용자 메모 영역을 구분하는 템플릿을 제안한다. 사용자 편집 충돌을 발견하면 CONFLICT로 기록하고 앱 원본 데이터에 역수입하지 않는다. 앱에서 정답·평가를 바꾸는 것은 앱의 정식 수정/재채점 경로로만 수행한다.

이번 연결 구조는 학습 콘텐츠·문제·풀이·오답·시험·평가·학습 기록의 매핑을 지원한다. 기존 Notion 구상에 있던 경력/실무·채용 정보 DB는 해당 앱 도메인의 화면/API가 확정되지 않았으므로 이번 업무 스키마에 임의로 추가하지 않았다.

14. 조회·운영 설계

핵심 조회는 사용자+날짜, 사용자+최근 풀이, 복습 예정 시각, 진행 중 시험 마감, 사용자 알림함, 상태+다음 작업 시각 순이다. 목록은 안정적인 정렬 키 (created_at,id) 등으로 페이지를 나누고, 같은 시각에 여러 행이 있어도 누락되지 않게 한다. 최종 커서 형식은 API 명세에 반영한다.

N+1 쿼리와 대시보드의 행 증폭을 피하도록 집계를 도메인별 서브쿼리로 분리한다. 풀이×세션×오답을 단순 조인한 뒤 COUNT하면 중복 집계될 수 있으므로 원천별로 먼저 집계하거나 DISTINCT 대상을 명확히 정한다.

초기에는 PostgreSQL 단일 DB와 애플리케이션 작업자로 시작한다. Redis, Kafka, 파티셔닝, 벡터 DB는 현재 필수 요구가 아니므로 추가하지 않는다. AI 대화와 outbox 크기는 보존 정책 및 실제 사용량을 측정한 뒤 관리한다.

DB 접속 역할은 최소한 마이그레이션 역할과 애플리케이션 역할을 분리한다. 애플리케이션 역할에 스키마 변경 권한을 주지 않는다. 프런트엔드·브라우저는 DB 자격증명을 갖지 않는다. 세션 쿠키 보안·CSRF·로그아웃 무효화·외부 연결 해제는 인증 구현의 통합 테스트 대상이다.

백업 주기·복구 목표·데이터 보존 기간은 아직 확정되지 않았다. 운영 시작 전에 암호화 백업과 실제 복원 연습, 탈퇴·연결 해제·비밀키 교체·장애 후 작업 복구 절차를 승인해야 한다. 법정 보존 기간이 있다고 추정해 임의 숫자를 넣지 않는다.

15. 구현과 검증 순서

15.1 구현 순서

1단계는 30개 학습·시험 원천 테이블을 사용하는 사용자·커리큘럼·개인 일정·문제·오답·시험·월말 평가 기능이다. 2단계는 AI와 outbox/중복 방지/감사 8개, 3단계는 알림과 외부 동기화 8개를 연결한다. 단계는 구현 순서이며 사용자 요청 기능을 제외한다는 의미가 아니다.

단, DDL의 참조 방향에는 1단계 콘텐츠에서 2단계 AI 작업을 참조하는 후방 FK가 있다. 제공한 SQL은 전체 테이블 생성 뒤 모든 FK를 추가한다. 운영 Flyway 파일로 나눌 때는 테이블 생성→후방 FK→인덱스/코드 데이터의 순서를 맞춰야 한다. 이미 운영에 적용된 마이그레이션은 수정하지 않고 새 변경 파일로 추가하는 프로젝트 운영 원칙을 둔다.

실제 엔티티·JPA Auditing·@Version·DTO·트랜잭션 테스트와 함께 마이그레이션을 정제한다. 프레임워크 세션 스키마는 선택한 Spring Session 버전의 PostgreSQL 스크립트를 사용하고, 자동 초기화와 Flyway가 동시에 같은 테이블을 만들지 않도록 구성한다. [S3]

15.3 현재 검증 수준

자동 검사한 것은 테이블·컬럼 명 중복, FK 컬럼 존재, FK 자료형 일치, 참조 대상이 PK/유니크인지 여부, 생성 파일 간 개수 일치다. 정적 참조 오류는 발견되지 않았다.

PostgreSQL 서버 실행, 전용 PostgreSQL SQL 파서 검사, Flyway 적용, JPA 매핑, 두 트랜잭션의 경합, 실제 Notion/Slack/Push 통신은 수행하지 않았다. Mermaid 원본 자체를 Mermaid 엔진으로 렌더링한 검사도 하지 않았다. HTML의 SVG 구조도는 같은 메타데이터에서 별도 생성한다. 이 차이를 validation.md에 기록한다.
