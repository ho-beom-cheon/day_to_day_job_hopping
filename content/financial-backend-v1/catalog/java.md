GA 채널에서 동일한 청약 요청을 중복 제거하려고 요청 객체를 HashSet에 넣었다. 화면에는 같은 청약 번호인데 집합에는 두 건이 남는다. 객체 참조가 같은 것과 업무상 같은 요청인 것은 다르다. equals가 같다고 판단하는 두 객체는 hashCode도 같아야 한다. 역방향은 성립하지 않으므로 해시 충돌만으로 중복이라고 처리해서는 안 된다. 비교 필드에는 변경 가능한 표시 이름보다 업무가 정한 불변 식별자를 사용한다.

보험료 합계와 정산 금액이 소수점 끝자리에서 다르다. BigDecimal을 사용했다는 사실만으로 정책이 일치하지는 않는다. 입력을 double에서 만들었는지 문자열에서 만들었는지, 중간 단계와 최종 단계 중 언제 반올림했는지 확인한다. equals는 값과 scale을 함께 비교하지만 compareTo는 수치 대소를 비교한다. 따라서 2.0과 2.00의 수치 동등성과 자료 표현의 동일성은 별개다.


## 실습과 해설

!! 0.005를 각각 반올림하면 0.02이고 먼저 합산하면 0.01이다. 반올림 위치를 업무 계약으로 정해야 한다.

## 상황과 원리
UTC로 저장한 거래를 한국 업무일별로 조회했더니 자정 부근 거래가 전날에 들어갔다. Instant는 타임라인의 순간, LocalDate는 날짜, LocalDateTime은 시간대 없는 날짜·시각이다. 서로 대체 가능한 타입이 아니다. 업무일은 지점 휴일과 마감 규칙에 따라 달라질 수도 있으므로 서버의 오늘 날짜만으로 결정하지 않는다.

## 상황과 원리

@@ java-atomicity|volatile·원자 연산·복합 조건의 차이|심화|concurrent
## 상황과 원리

## 수정과 영향

?? volatile만 적용한 count++에서 증가가 사라질 수 있는 이유는?
+ 읽기·계산·쓰기 전체가 원자적으로 보호되지 않기 때문
- volatile이 항상 값을 0으로 초기화하기 때문
- synchronized가 다른 서버까지 자동 전파되기 때문

@@ java-state-machine|상태 전이와 도메인 불변식|심화|enum
## 상황과 원리
신청 상태를 문자열로 받아 DB에 그대로 저장하자 승인 없이 실행 완료가 되었다. enum은 허용되는 이름을 제한할 수 있지만 전이 규칙까지 자동으로 보장하지 않는다. 상태 변경에는 현재 상태·요청 행위·행위자 권한·정책 버전·동시 요청을 함께 고려해야 한다.
## 판단 자료
```text
학습용 전이: REQUESTED -> APPROVED -> EXECUTED
APPROVED -> CANCELED 허용, EXECUTED -> CANCELED 금지
T1 실행과 T2 취소가 APPROVED를 동시에 읽음
```
## 수정과 영향
가능한 전이를 명시하고 현재 상태 또는 버전을 조건으로 갱신한다. 영향 행 수가 0이면 다른 요청이 먼저 바꿨을 수 있으므로 재조회·충돌 응답 정책을 적용한다. 외부 실행 성공 뒤 로컬 저장이 실패할 수 있으므로 한 JVM의 상태 전이 검사만으로 분산 일관성이 완성되지 않는다. 실행 취소는 원거래 삭제보다 별도 보상 거래가 필요한 경우가 있으며 업무 규칙에 따라 정한다.
## 실습과 해설
모든 상태×행위 표에서 허용과 거부를 먼저 정리한다. 중복 승인, 중복 실행, 실행/취소 경쟁, 이미 완료된 거래 재시도를 확인한다. 오류 응답만 보지 말고 최종 상태와 이력 개수, 외부 실행 횟수를 확인한다. 면접에서는 상태 패턴을 썼다는 이름보다 어떤 불변식을 어디에서 강제했는지 설명한다. 이 예시는 실제 담당 프로젝트의 구현 사실이 아니라 설계 연습이다.
