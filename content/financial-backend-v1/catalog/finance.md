@@ finance-credit-flow|여신 신청·심사·승인·실행의 상태 구분|기초|credit
## 업무 개념
여신은 금융기관이 신용을 제공하는 업무다. 신청 접수, 심사, 승인, 약정, 실행, 상환, 사후 관리는 구분되는 단계다. 승인되었다고 실제 자금이 지급된 것은 아니다. 이 자료는 은행 업무를 이해하기 위한 가상 설계이며 KDB에서 직접 여신을 구현했다는 경력으로 사용하지 않는다.
## 판단 자료
```text
가상 정책: 승인 한도 1억원, 실행 요청 3000만원
승인=조건에 따른 허용 결정
실행=조건 확인 후 실제 자금 지급과 채권 발생 기록
승인 만료 뒤 실행 요청 -> 정책상 재확인 필요
```
## 설계와 영향
각 단계의 허용 행위, 필수 서류, 결정 주체, 유효 기간을 상태 전이로 정리한다. 조건부 승인과 실행 전 조건 확인을 별도로 표현한다. 단일 approved=true로 모든 단계를 나타내면 지급 여부와 잔여 한도, 취소 가능 범위를 알기 어렵다. 단계별 입력과 판단 당시 정책 버전을 보존한다.
## 실습과 해설
정상 실행, 승인 거절, 승인 만료, 부분 실행, 중복 실행의 상태 표를 만든다. 기대 결과에는 상태뿐 아니라 실제 지급 횟수와 잔여 한도, 이력을 포함한다. 면접에서는 ‘승인과 실행이 왜 다른가’에 업무 의미와 재시도·감사 영향까지 답한다. 실제 상품 규정·금리·기간은 해당 기관의 최신 문서로 확인해야 한다.
?? 승인만 완료된 건을 실행 완료로 표시하면 무엇을 잃는가?
+ 실제 지급 여부와 실행 전 조건 확인의 구분
- 신청자의 화면 테마
- 모든 이력의 필요성
- 승인 한도가 반드시 전액 실행된다는 사실
!! 허용 결정과 실제 자금 이동은 별개의 업무 사실이다.

@@ finance-credit-assessment|신용평가·담보·상환능력의 구분|기초|credit
## 업무 개념
신용 위험은 약정된 의무가 이행되지 않을 가능성과 손실에 관련된다. 상환능력, 신용 이력, 담보, 보증은 판단의 서로 다른 요소다. 담보가 있다는 사실만으로 차주의 현금흐름이나 심사 절차를 생략할 수 없다. 개발자는 승인 공식을 임의로 만들기보다 입력·정책·결정 근거를 추적할 수 있게 설계한다.
## 판단 자료
```text
가상 심사 입력: 재무자료 기준일, 현금흐름, 기존 채무, 담보 평가일
오류 사례: 최신 평가에 2년 전 재무자료가 조용히 재사용됨
요구: 사용한 자료 버전과 판단 시점 보존
```
## 설계와 영향
평가 결과와 사람이 승인한 결과를 구분하고 override에는 권한과 사유를 기록한다. 누락 정보를 0으로 바꾸면 ‘없음’과 ‘미확인’이 혼동된다. 모델·등급 정책 변경 시 과거 결정을 현재 규칙으로 덮어쓰지 않는다. 실제 등급 구간이나 승인 기준은 기관별 정책이며 이 자료는 특정 대출 자격을 안내하지 않는다.
## 실습과 해설
자료 누락, 만료, 상충 자료, 재평가, 수동 조정의 입력을 만들고 처리 상태를 정한다. 승인 여부를 상상해서 채우지 말고 필요한 추가 확인을 명시한다. 면접에서는 신용·담보·심사의 용어와 데이터 품질·버전·감사 연결을 설명한다.
?? 심사 자료 누락을 0으로 저장하는 문제는?
+ 미확인과 실제 0이라는 서로 다른 사실을 합쳐 잘못된 판단을 유도함
- 자료 버전이 자동으로 최신화됨
- 담보가 있으면 모든 자료가 불필요함
- 개발자가 임의 승인 기준을 정해도 됨
!! 누락 상태와 업무상 수치를 분리해서 저장하고 판단해야 한다.

@@ finance-limit|약정 한도·사용액·예약액의 불변식|실무|credit
## 업무 개념
한도 거래에서는 약정 한도, 이미 사용한 금액, 진행 중인 예약 금액을 구분할 수 있다. 가용액을 한도에서 사용액만 빼서 계산하면 동시에 진행되는 실행 요청이 한도를 초과할 수 있다. 예약은 실제 실행과 다르며 만료·취소·실행 전환 정책이 필요하다.
## 판단 자료
```text
가상 규칙: 가용=한도100-사용60-예약30=10
신규 실행 20 -> 현재 가용 부족
예약30 실행 전환: 사용90, 예약0, 가용10
```
## 설계와 영향
예약과 실행 전환을 원자적으로 갱신하고 요청 식별자로 중복 차감을 막는다. timeout 뒤 예약을 무조건 풀면 외부에서 실행된 거래의 한도가 되살아날 수 있다. 먼저 외부 상태를 확인하거나 불명 상태를 유지하는 계약을 둔다. 예약 정리 작업은 기한뿐 아니라 실제 실행 여부를 고려한다.
## 실습과 해설
동시 예약, 예약 만료와 실행 경쟁, 중복 실행 통지, 실행 실패를 검증한다. 가용액뿐 아니라 사용+예약이 한도를 넘지 않는 불변식을 확인한다. 면접에서는 단순 뺄셈과 분산 상태 전환의 차이를 설명한다. 숫자는 원리를 위한 가상 단위다.
?? 예약30이 실제 실행될 때 올바른 상태 전환은?
+ 사용액을 30 늘리고 예약액을 30 줄여 가용액을 유지
- 사용액과 예약액을 모두 30 늘림
- 예약을 삭제하고 사용액을 그대로 둠
- 응답이 늦으면 무조건 한도를 30 늘림
!! 예약에서 사용으로 이동하는 동일 업무 금액을 두 번 차감하거나 해제하지 않아야 한다.

@@ finance-interest|이자 계산의 기준일·일수·반올림|실무|decimal
## 업무 개념
단리 예제는 원금×연이율×기간 비율로 생각할 수 있지만 실제 계산에는 일수 기준, 시작/종료일 포함, 금리 변경, 통화와 반올림 정책이 필요하다. 연이율만 알아서는 정답이 하나로 정해지지 않는다. 아래는 교육용 가정이며 실제 대출 상품의 계산 안내가 아니다.
## 판단 자료
```text
가정: 원금1,000,000 / 연 3.65% / 10일 / 365일 기준
1,000,000 × 0.0365 × 10 / 365 = 1,000
시작일 포함·종료일 제외, 중간 반올림 없음 가정
```
## 설계와 영향
계산 입력에 원금 잔액·기간·금리 버전·일수 규칙·반올림 위치를 남긴다. 기간 중 금리가 바뀌면 구간을 나눌 수 있으며 변경일을 어느 구간에 넣는지 명확히 한다. 동일 계산을 화면·배치·코어에서 각각 구현하면 정책 불일치 위험이 커진다.
## 실습과 해설
0일, 금리 변경일, 윤년, 일부 상환 직전/직후를 표로 만든다. 이 예제의 365일 가정을 다른 상품에 일반화하지 않는다. 손계산과 BigDecimal 계산을 비교하고 금액 차이가 생기면 먼저 기간·정책부터 확인한다. 면접에서는 공식 암기보다 재현 가능한 계산 계약을 설명한다.
?? 위 명시된 가정에서 이자는?
+ 1,000
- 10,000
- 365
- 금리만 있으므로 위 가정을 사용해도 계산 불가
!! 모든 필요한 교육용 가정이 주어졌고 식의 결과는 1,000이다.

@@ finance-repayment|원금균등·원리금균등의 현금흐름|기초|credit
## 업무 개념
원금균등은 회차별 원금 상환을 일정하게 두는 방식이며 잔액이 줄어들수록 같은 금리·기간 가정에서 이자도 줄어든다. 원리금균등은 일정한 조건에서 회차별 원금과 이자의 합을 일정하게 설계한다. 만기일시상환은 만기에 원금을 상환하는 구조다. 실제 상품은 금리 변경·유예·수수료 조건에 따라 달라진다.
## 판단 자료
```text
가상 원금300, 3회 원금균등, 매 회차 이율10%
회차1: 원금100+이자30=130
회차2: 원금100+이자20=120
회차3: 원금100+이자10=110
```
## 설계와 영향
약정 스케줄과 실제 입금·배분 결과를 분리한다. 일부 입금이나 중도상환이 발생하면 원래 스케줄을 덮어쓰기보다 변경 이력과 적용 기준을 보존한다. 마지막 회차의 반올림 잔여액 처리도 명시한다. 금리나 주기가 다르면 같은 표를 그대로 재사용할 수 없다.
## 실습과 해설
위 표의 원금 합계300, 이자 합계60, 최종 잔액0을 확인한다. 일부 입금과 연기 상황에서 무엇이 예정이고 무엇이 실제인지 표시한다. 면접에서는 세 상환 방식의 차이와 스케줄·원장 데이터의 분리를 설명한다.
?? 위 원금균등 예제에서 두 번째 납입 총액은?
+ 120
- 130
- 110
- 100
!! 첫 회차 후 잔액200의 이자20과 원금100을 합친다.

@@ finance-allocation|부분 상환과 입금 배분 순서|실무|credit
## 업무 개념
입금액이 청구 총액보다 적으면 이자·원금·비용 중 어디에 먼저 배분할지 규칙이 필요하다. 배분 순서는 기관·상품·계약과 관련 규정에 따라 정하며 개발자가 임의로 일반화해서는 안 된다. 같은 입금을 다시 처리할 때 배분 결과가 중복되지 않아야 한다.
## 판단 자료
```text
가상 규칙: 이자 먼저, 그다음 원금; 비용 없음
청구 이자20, 원금100 / 입금70
배분: 이자20, 원금50 / 미상환 원금50
```
## 설계와 영향
입금 원거래, 배분 내역, 적용 규칙 버전을 연결한다. 취소 시 현재 규칙으로 역산하기보다 원래 배분을 참조해 반대 효과를 기록한다. 초과 입금이나 여러 계약에 대한 배분은 별도 정책이다. 수납 성공과 채권 잔액 반영 성공 사이의 실패도 대사 대상으로 둔다.
## 실습과 해설
0원, 이자보다 적은 입금, 정확한 총액, 초과 입금, 같은 입금 재전송을 검증한다. 입금액=배분액+미배분액 관계를 확인한다. 면접에서는 일부 상환을 단순 잔액 감소로 처리하지 않고 근거를 남기는 이유를 설명한다.
?? 위 가상 규칙에서 70 입금의 원금 배분액은?
+ 50
- 70
- 20
- 100
!! 이자20을 먼저 배분하고 남은50을 원금에 적용한다.

@@ finance-delinquency|연체 판단과 사후 관리 이벤트|실무|credit
## 업무 개념
상환 예정일이 지났다고 모든 상품에서 같은 연체 상태가 되는 것은 아니다. 영업일 조정·입금 반영 시점·유예·정책 버전이 영향을 줄 수 있다. 개발 학습에서는 기한, 실제 수납, 판단 기준일, 예외 승인을 분리해 모델링한다. 실제 연체이율이나 규제 기한을 이 자료에서 정하지 않는다.
## 판단 자료
```text
가정: 10일 납부 기한, 유예 없음, 기준일 11일
필요 금액100, 반영된 수납60 -> 미납40
늦게 도착한 10일자 입금 이벤트가 추가될 수 있음
```
## 설계와 영향
연체 판정의 입력과 실행 시점을 남기고 지연 입금으로 재판정할 때 이전 통지·조치의 상태를 연결한다. 현재 잔액만 보면 과거 판단을 재현하기 어렵다. 고객에게 나가는 통지는 별도 발송 상태와 멱등 키로 관리한다. 판정과 실제 외부 발송을 같은 성공 표시로 묶지 않는다.
## 실습과 해설
부분 입금, 지연 도착, 판정 재실행, 유예 승인, 통지 실패를 검증한다. 미납 금액과 업무 상태, 발송 횟수를 각각 확인한다. 면접에서는 사후 관리가 단순 날짜 비교를 넘어 데이터 도착과 정책 이력을 다룬다고 설명한다.
?? 지연 입금 이벤트를 처리할 때 필요한 것은?
+ 당시 기준일과 원래 입금 시점·반영 시점을 구분한 재판정
- 현재 시각으로 입금일을 무조건 변경
- 이전 통지 기록 삭제
- 모든 상품에 같은 연체 규칙 적용
!! 업무 시점과 시스템 반영 시점을 구분해야 늦게 도착한 사실을 정확히 처리할 수 있다.

@@ finance-ledger|업무 원장·잔액·거래 이력의 역할|기초|aggregate
## 업무 개념
잔액 숫자만 저장하면 어떤 거래로 그 잔액이 되었는지 설명하기 어렵다. 원장은 거래 사실과 관련 금액 변화를 추적하는 기준 자료이며 조회용 집계나 화면 캐시와 구분한다. 여기서는 단순한 거래 합계 모형을 사용하며 실제 기관의 회계 계정 체계를 단정하지 않는다.
## 판단 자료
```text
기초 잔액100
거래 T1 +50, T2 -20 -> 기말 잔액130
T2 취소: 원거래 참조한 +20 조정 ->150
T2 행 자체 삭제는 과거 판단 근거를 지움
```
