@@ sql-grain|JOIN 전에 정하는 결과 행의 단위|기초|join
## 상황과 원리
KDB 기업 현황과 이력을 JOIN했더니 기업 수가 늘었다. 쿼리를 쓰기 전에 결과 한 행이 기업인지 계약인지 이력인지 정한다. 1:N 관계를 연결하면 기준 행이 반복되는 것은 자연스럽다. 오류는 그 결과를 기업 한 건으로 가정해 합계나 페이지 수를 계산하는 데 있다.
## 판단 자료
```text
기업 A: 계약 2개, 담당자 3명
계약과 담당자를 각각 기업에 JOIN -> 조합 6행
각 계약 금액 100, 200 -> 잘못 합산하면 900
원하는 계약 합계는 300
```
## 수정과 영향
계약을 기업 단위로 먼저 집계한 뒤 결합하거나 필요한 존재 여부만 EXISTS로 확인한다. DISTINCT로 숫자 중복을 지우면 같은 금액인 서로 다른 계약이 사라질 수 있다. 화면 목록과 전체 건수 쿼리가 같은 기준 집합을 사용하는지도 확인한다. LEFT JOIN 뒤 WHERE 조건은 NULL 확장 행을 제거할 수 있으므로 조건 위치의 의미를 살핀다.
## 실습과 해설
관계 0/1/여러 건을 가진 기업을 만든다. JOIN 단계마다 행 수와 합계를 적고 증가가 시작되는 단계를 찾는다. 기대값은 기업 수 1, 계약 수 2, 계약 합계 300이다. 면접에서는 쿼리 문법보다 기준 행과 관계의 수를 먼저 설명하고, 집계 전후에 어떤 데이터가 보존되는지 말한다.
?? 위 데이터에서 계약 합계가 900이 된 원인은?
+ 담당자 3명과 결합되며 각 계약 행이 세 번 반복됨
- SUM이 자동으로 수수료를 붙임
- 두 계약의 금액이 반드시 같음
- 기업 ID가 숫자가 아님
!! 서로 독립적인 1:N 관계를 함께 연결하면 곱으로 행이 늘 수 있다.

@@ sql-index-order|복합 인덱스의 선두 열과 검색 범위|실무|indexes
## 상황과 원리
기업별 거래를 기간으로 조회하는데 인덱스가 있어도 느리다. 인덱스 존재 여부보다 필터·정렬·선택도·반환량과 열 순서를 봐야 한다. PostgreSQL 17 B-tree 복합 인덱스에서는 선두 열의 조건이 탐색 범위 제한에 중요하다. 이 원리를 모든 DB와 모든 인덱스 종류에 그대로 일반화하지 않는다.
## 판단 자료
```sql
SELECT id, occurred_at FROM trade
WHERE company_id = 17 AND occurred_at >= :from_time
ORDER BY occurred_at, id LIMIT 50;
-- 후보 인덱스: (company_id, occurred_at, id)
```
## 수정과 영향
동등 조건 다음에 범위·정렬을 고려한 후보를 만들고 실제 계획을 비교한다. company_id만 조회하는 경로와 전체 기업의 날짜 조회 경로는 요구가 다르다. 인덱스는 쓰기와 저장 비용을 늘리므로 모든 조합을 추가하지 않는다. 반환 컬럼을 모두 인덱스에 넣는 것도 폭과 갱신 비용을 확인해야 한다.
## 실습과 해설
기업별 분포가 균등한 경우와 특정 기업에 몰린 경우를 비교한다. 선택도가 높은/낮은 날짜 범위로 계획·실제 행·버퍼를 확인한다. 작은 테이블에서 순차 스캔이 선택됐다고 인덱스가 고장 났다고 결론 내리지 않는다. 면접에서는 KDB에서 실제 했던 조회 개선과 여기서 학습한 인덱스 가설을 구분한다.
?? 인덱스를 추가한 뒤 반드시 비교할 것은?
+ 실제 조회 조건별 계획·반환량·읽기 비용과 쓰기 영향
- 인덱스 이름의 길이만
- 모든 요청에 같은 인덱스가 강제되는지만
- 순차 스캔이면 무조건 실패라고 표시
!! 인덱스의 효과는 데이터 분포와 조회 경로에 따라 달라진다.

@@ sql-explain|실행 계획의 추정·실측·반복 횟수|실무|explain
## 상황과 원리
실행 계획의 cost를 밀리초로 읽고 개선했다고 보고했다. cost는 플래너의 상대적인 추정 비용이며 실제 실행 시간과 같은 단위가 아니다. EXPLAIN ANALYZE는 쿼리를 실제 실행한다. 변경 쿼리에 적용하면 부작용이 발생하므로 합성 데이터나 격리 환경에서 검증한다.
## 판단 자료
```text
노드 예상 rows=10, 실제 rows=10000
Nested Loop 내부 노드 loops=1000
작은 내부 비용도 반복 횟수와 결합해 전체 지연을 만들 수 있음
```
## 수정과 영향
추정과 실측 행 수가 크게 다른 위치에서 통계·상관 관계·필터를 확인한다. 반복 조회가 많다면 결합 전략과 인덱스, 쿼리 구조를 검토한다. 캐시가 데워진 실행과 첫 실행을 섞어 비교하지 않는다. 버퍼 hit도 공짜라는 뜻은 아니며 총 CPU와 반환 데이터 비용을 함께 살핀다.
## 실습과 해설
같은 파라미터·데이터·환경으로 여러 번 측정하고 중앙값과 지연 분포를 기록한다. 전후 결과 집합이 동일한지 먼저 확인한 뒤 성능을 비교한다. 계획 한 번만으로 모든 파라미터의 성능을 보장하지 않는다. 면접에서 측정하지 않은 개선율을 만들지 말고 확인한 조건과 남은 한계를 말한다.
?? EXPLAIN의 cost를 실제 밀리초로 보고하면 안 되는 이유는?
+ 추정 비용의 단위와 실제 경과 시간은 다르기 때문
- ANALYZE는 쿼리를 전혀 실행하지 않기 때문
- rows는 항상 실제 측정값이기 때문
- loops는 성능과 무관하기 때문
!! 추정치와 실행 시 측정한 시간·행 수를 구별해서 설명해야 한다.

@@ sql-keyset|OFFSET과 키셋 페이지의 일관성|실무|select
## 상황과 원리
거래 목록 첫 페이지를 본 뒤 새 거래가 추가되자 두 번째 페이지에 같은 거래가 다시 나타났다. OFFSET은 그 순간 정렬된 결과에서 행 수만큼 건너뛴다. 결과가 바뀌면 위치도 바뀐다. 정렬 열이 동률이면 고유한 추가 정렬 키가 필요하다.
## 판단 자료
```sql
SELECT id, occurred_at FROM trade
WHERE (occurred_at, id) < (:cursor_time, :cursor_id)
ORDER BY occurred_at DESC, id DESC LIMIT 20;
-- PostgreSQL 예제: 두 커서 컬럼 모두 NOT NULL 가정
```
## 수정과 영향
마지막 행의 정렬 키를 커서로 사용하면 깊은 offset 비용과 일부 위치 이동 문제를 줄일 수 있다. 그러나 과거 행의 정렬 값이 수정되면 여전히 결과가 달라질 수 있다. 완전한 조회 스냅샷이 필요하면 기준 시점·불변 순번·별도 스냅샷 정책을 정한다. 임의 페이지 점프가 필요한 UI에서는 키셋의 제약도 고려한다.
## 실습과 해설
시각 동률 3건, 페이지 사이 신규 삽입, 기존 행 삭제, 정렬 값 변경을 검증한다. 중복/누락 여부와 전체 집합의 기준을 기록한다. 커서에는 필터 조건도 연결해 다른 검색의 커서를 재사용하지 않도록 한다. 면접에서는 단순히 키셋이 빠르다고 말하지 말고 지원할 탐색 방식과 일관성 수준을 설명한다.
?? 시각만 커서로 사용할 때 동률 거래를 놓칠 수 있는 이유는?
+ 같은 시각의 여러 행을 고유하게 구분하는 정렬 키가 없어서
- DESC가 항상 중복을 제거해서
- LIMIT가 전체 스냅샷을 생성해서
- OFFSET이 데이터 변경을 금지해서
!! 정렬과 커서 조건에 일관된 동률 해소 키가 필요하다.

@@ sql-window-aggregate|GROUP BY와 윈도 함수의 결과 단위|기초|window
## 상황과 원리
거래 행을 유지하면서 고객별 누계를 보여줘야 한다. GROUP BY는 그룹별로 결과 행을 줄이고, 윈도 함수는 각 행을 유지한 채 파티션 내 계산을 붙일 수 있다. ORDER BY와 프레임을 어떻게 지정하는지에 따라 동률 행의 누계가 달라질 수 있다.
## 판단 자료
```text
고객 A 거래: (id1,10), (id2,20), (id3,-5)
id 순서 누계: 10,30,25
고객별 최종 합계 한 행: A,25
```
## 수정과 영향
행별 누계에는 결정적인 순서와 ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW 같은 의도한 프레임을 명시한다. 기간 필터를 누계 계산 전후 어디에 두는지에 따라 기간 내 누계와 전체 누계 표시가 달라진다. 외부 SELECT로 감싼 뒤 필터하는 방식은 계산 대상 집합을 유지할 때 유용하다.
## 실습과 해설
금액이 음수인 취소, 같은 시각 두 거래, 기간 시작 전 잔액을 포함한 데이터를 만든다. 기대 누계를 손으로 계산하고 결과와 비교한다. 기본 프레임에 의존한 쿼리와 명시적 ROWS 쿼리를 비교한다. 면접에서는 집계 함수 이름보다 결과의 한 행과 누계 시작점을 어떻게 정했는지 설명한다.
?? 행별 거래와 누계를 동시에 보여주려면 무엇을 먼저 정해야 하는가?
+ 고객별 파티션, 안정적인 거래 순서, 누계 계산 범위
- GROUP BY가 항상 원래 행을 유지한다는 가정
- 음수 거래는 모두 제거한다는 가정
- 기본 프레임이 모든 업무 요구와 같다는 가정
!! 윈도 결과는 대상 집합·순서·프레임에 따라 결정된다.

@@ sql-isolation|격리 수준과 읽기 스냅샷|심화|isolation
## 상황과 원리
같은 트랜잭션에서 잔액 합계를 두 번 읽었는데 값이 달라졌다. PostgreSQL READ COMMITTED에서는 각 명령이 시작하는 시점의 스냅샷을 사용하므로 다른 트랜잭션의 커밋을 다음 조회에서 볼 수 있다. 트랜잭션 안이라는 이유만으로 모든 조회가 같은 시점을 본다고 가정하지 않는다.
## 판단 자료
```text
T1 SELECT sum -> 100
T2 INSERT 20; COMMIT
T1 SELECT sum -> 120 가능 (READ COMMITTED)
```
## 수정과 영향
한 보고서에 동일 기준 시점이 필요하면 단일 쿼리 또는 요구에 맞는 격리 정책을 검토한다. 더 높은 격리 수준은 대기·충돌·재시도 비용을 동반할 수 있다. SERIALIZABLE도 모든 업무를 실패 없이 순차 실행한다는 뜻은 아니며 직렬화 실패 처리가 필요하다. DB 제품별 같은 격리 이름의 세부 동작이 다를 수 있다.
## 실습과 해설
두 연결로 위 순서를 제어하고 설정별 결과와 실패를 기록한다. 읽기 일관성과 갱신 충돌 방지는 별도 테스트로 나눈다. 재시도는 전체 트랜잭션 입력과 외부 부작용을 고려해야 한다. 면접에서는 필요한 업무 불변식을 먼저 설명한 뒤 격리 수준을 선택한다.
?? READ COMMITTED에서 같은 트랜잭션의 두 SELECT가 다른 합계를 볼 수 있는 이유는?
+ 각 명령 시작 시점의 스냅샷 사이에 다른 트랜잭션이 커밋할 수 있어서
- 트랜잭션이 자동으로 모든 읽기를 캐시해서
- COMMIT이 이전 조회를 소급 변경해서
- SELECT가 항상 데이터를 삭제해서
!! 같은 트랜잭션과 같은 스냅샷을 구분해야 한다.

@@ sql-lock-order|행 잠금·교착·일관된 잠금 순서|심화|locks
## 상황과 원리
두 계좌 사이 이체가 가끔 교착으로 실패한다. 각 요청이 출금 계좌를 먼저 잠그면 A→B와 B→A 요청이 서로의 잠금을 기다릴 수 있다. 잠금은 정합성을 위한 도구지만 획득 순서와 보유 시간이 운영 안정성을 결정한다.
## 판단 자료
```text
T1 lock A -> wait B
T2 lock B -> wait A
대안: 두 요청 모두 작은 계좌 ID부터 잠금 획득
```
## 수정과 영향
여러 행을 잠그는 경로에 일관된 순서를 적용하고 트랜잭션 안의 원격 호출을 줄인다. 교착 검출로 중단된 트랜잭션은 업무 전체를 안전하게 재시도할 수 있는지 검토한다. NOWAIT/SKIP LOCKED는 대기 정책을 바꾸지만 빠진 행을 허용하지 않는 금융 조회에 무작정 적용하면 안 된다.
## 실습과 해설
두 연결의 잠금 순서를 교차시켜 교착을 재현한다. 실패한 요청의 모든 변경이 롤백되었는지, 재시도 후 합계가 보존되는지 확인한다. 로그에는 거래 ID와 잠금 대기 구간을 남기고 민감한 전체 계좌 정보는 제한한다. 면접에서는 교착을 없애려 잠금을 전부 제거하는 대신 불변식과 잠금 순서를 설명한다.
?? 반대 방향 이체 두 건의 교착 가능성을 줄이는 방법은?
+ 두 요청 모두 같은 기준으로 계좌 잠금 획득 순서를 정함
- 항상 자기 출금 계좌부터 잠금
- 모든 잠금 오류를 성공으로 응답
- SKIP LOCKED로 잠긴 계좌를 없는 계좌로 간주
!! 일관된 획득 순서는 순환 대기의 주요 원인을 줄인다.

@@ sql-conditional-update|선조회 경쟁과 조건부 UPDATE|실무|update
## 상황과 원리
잔여 한도 100을 두 요청이 읽고 각각 80을 사용했다. 애플리케이션에서 먼저 검사하고 나중 저장하는 사이에 경쟁이 생겼다. 업무 조건과 갱신을 같은 저장 명령에 넣으면 검사 시점과 저장 시점 사이의 틈을 줄일 수 있다.
## 판단 자료
```sql
UPDATE credit_limit SET available = available - 80
WHERE id = :id AND available >= 80;
-- 성공 판정: 영향 행 수 1
```

## 상황과 원리
제외 목록을 NOT IN으로 적용했더니 예상한 행이 모두 사라졌다. SQL의 NULL은 일반 값과 같은 비교 규칙을 쓰지 않는다. 비교 결과가 UNKNOWN일 수 있고 WHERE는 TRUE인 행만 남긴다. NULL을 빈 문자열이나 0과 같은 값으로 취급하면 업무 의미가 바뀐다.

```text

```
## 수정과 영향
제외 집합의 NULL 의미를 정하고 필요한 경우 NOT EXISTS로 관계를 표현한다. NOT EXISTS도 내부 비교 컬럼의 NULL 정책까지 자동으로 정해 주지는 않는다. 집계 COUNT(*)와 COUNT(column)은 NULL 포함 여부가 다르다. COALESCE로 일괄 치환하면 미입력과 실제 0을 구분할 수 없게 될 수 있다.
## 실습과 해설
NULL 없음·NULL만 있음·빈 제외 집합·실제 0을 가진 입력을 비교한다. 결과 행 수와 집계 수를 손으로 예측한다. 수정 전후 업무 집합이 같은지 확인하고 단순히 결과가 나온다는 이유로 성공 처리하지 않는다. 면접에서는 3값 논리의 실무 영향과 NULL의 업무 정의를 연결한다.
?? 제외 목록에 NULL이 들어간 NOT IN에서 예상 행이 사라지는 이유는?
+ 비교가 UNKNOWN이 되어 WHERE의 TRUE 조건을 통과하지 못할 수 있어서
- NULL이 모든 숫자와 같아서
- NOT IN이 자동으로 NULL을 무시해서
- COUNT가 행을 삭제해서
!! SQL 비교에서 UNKNOWN과 FALSE는 다르지만 WHERE에서는 둘 다 결과에 포함되지 않는다.
