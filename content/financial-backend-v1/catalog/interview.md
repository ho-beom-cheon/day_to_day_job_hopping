## 답변 원리
‘API로 연동했다’ 뒤에는 요청 경로, 성공의 의미, 오류 처리, 재시도, 권한, 데이터 변환 질문이 이어진다. C# 채널과 코어 사이에서 직접 수정한 범위를 먼저 설명한다. 코어의 내부 저장 구조는 확인한 만큼만 말한다.
## 판단 자료
```text
Angular 화면 -> 채널 서버 -> 코어 API -> 채널 응답 -> 화면
상황: 채널 등록 성공처럼 보였으나 코어 조회에 아직 안 나타남
검토: 접수/완료 의미, 비동기 지연, 요청 ID, 상태 조회
```
## 답변 구성과 한계
한 API를 골라 입력 필드·변환 규칙·외부 응답·화면 표시를 그린다. HTTP 200과 업무 성공 코드가 다른지 확인했던 경험을 준비한다. timeout이면 미처리라고 단정하지 말고 당시 확인한 정책과 개선 아이디어를 나눈다. 인증 토큰이나 실제 고객 데이터를 면접 자료에 넣지 않는다.
## 실습과 해설
면접관이 ‘응답 유실이면 두 번 등록되지 않나’라고 물었다고 가정한다. 실제 구현을 알면 키·조회·재처리를 설명하고 모르면 확인할 계약과 안전한 설계 대안을 말한다. 답변은 원인 가설→증거→수정→테스트로 연결한다. 외부 시스템 전체를 본인이 설계했다고 확대하지 않는다.
?? ‘API 연동’ 경험 설명에 가장 필요한 추가 정보는?
+ 본인이 담당한 요청·응답 경계와 실패를 검증한 방법
- 코어 내부를 확인하지 않고 저장 구조를 단정
- 사용하지 않은 메시지 브로커를 추가
- 고객 원문을 그대로 면접 자료에 제시
!! 실제 책임과 검증 근거를 구체화해야 신뢰할 수 있는 답변이 된다.

@@ interview-ga-sync|동기화·조회·대사의 차이 설명|실무|aggregate
## 답변 원리
서로 데이터가 보인다는 사실만으로 실시간 양방향 동기화 구조를 단정하지 않는다. API를 호출해 바로 표시하는 조회, 복제 데이터를 갱신하는 동기화, 차이를 확인하는 대사는 다른 동작이다. 사용자의 GA 경험에는 조회와 등록 연계, 동기화 확인이 있었지만 구체적인 전송 기술은 별도 확인 대상이다.
## 판단 자료
```text
화면 A: 요청 시 코어 조회 결과 표시
화면 B: 이전 동기화 데이터 조회
검증 C: 쿼리로 양쪽 상태 불일치 확인
각각의 지연 원인과 복구 방법이 다름
```
## 답변 구성과 한계
화면별 데이터 원본·전파 시점·확인 방법을 설명한다. 중복·역순·누락을 처리했다면 구체적 근거를 제시한다. 당시 사용하지 않은 CDC/Kafka/outbox를 경험으로 말하지 말고 개선안으로 분리한다. DB 확인을 했다는 사실이 코어 DB를 직접 수정했다는 뜻도 아니다.
## 실습과 해설
‘계속 동기화된다는 것은 어떤 방식인가’에 90초로 답한다. 확인한 API 경로와 데이터 차이 재현을 말하고 미확인 전송 방식은 명시한다. 면접관이 원본 시스템과 충돌 해결을 물으면 실제 정책 또는 제안 정책을 구분한다. 좋은 답변은 모든 기술을 안다고 하는 것보다 경계가 정확하다.
?? API로 읽어 표시하는 화면을 설명할 때 피해야 할 단정은?
+ 실제 근거 없이 실시간 양방향 데이터 복제라고 표현
- 요청·응답 경로를 설명
- 지연된 데이터와 즉시 조회 결과를 구분
- 직접 확인한 불일치 사례를 제시
!! 관찰된 화면 결과만으로 내부 동기화 방식 전체를 추정하면 안 된다.

## 답변 원리
KDB 산업은행 기업 현황 조회·검색 경험은 결과 정확성과 성능을 함께 설명하면 강점이 된다. 어떤 사용자가 어떤 조건에서 불편했는지부터 말한다. 느리다는 관찰, 원인 가설, 실행 계획, 변경, 전후 측정 조건을 연결한다.
## 판단 자료
```text
답변 메모: 검색 조건 / 데이터 건수 / 반환 행 / 호출 횟수 / 실행 계획
```

## 실습과 해설
‘왜 인덱스가 원인이라고 봤나’, ‘다른 검색 조건은 느려지지 않나’, ‘정답 결과는 같나’에 답한다. 자료가 없으면 당시 확인 범위와 지금 추가할 측정 계획을 제시한다. 면접에서 이 경험을 여신 심사 시스템 전체 설계로 바꾸지 않는다.
?? 조회 성능 개선을 설명할 때 결과 정확성도 언급해야 하는 이유는?
+ 빠른 쿼리가 중복·누락·다른 업무 집합을 반환할 수 있어서
- 실행 시간이 짧으면 결과는 항상 같아서
- 인덱스가 업무 규칙을 자동 검증해서
- 테스트 없이 계획만 비교하면 충분해서
!! 같은 업무 결과를 유지했는지 확인한 뒤 성능 개선을 주장해야 한다.

## 답변 원리
