@@ spring-di-scope|의존성 주입과 싱글턴의 요청 상태|기초|di
## 상황과 원리
싱글턴 Service 필드에 현재 고객 번호를 저장한 뒤 코어를 호출했다. 두 요청이 겹치면 다른 고객 번호가 사용될 수 있다. 의존성 주입은 협력 객체를 연결하는 방식이며 요청별 데이터의 격리를 자동으로 제공하지 않는다. 기본 싱글턴 빈은 여러 요청에서 함께 사용되므로 가변 요청 상태는 메서드 인자·지역 변수로 전달하는 편이 명확하다.
## 판단 자료
```text
T1: service.customer = A
T2: service.customer = B
T1: core.lookup(service.customer) -> B
```
## 수정과 영향
생성자에는 클라이언트나 저장소 같은 의존성을 받고 고객 번호는 메서드 인자로 받는다. 요청 스코프가 필요한 경우 그 수명과 비동기 작업에 전파되는 범위를 확인한다. ThreadLocal을 대안으로 쓰면 스레드 풀 재사용에서 정리 누락이 생길 수 있다. 전체 메서드에 잠금을 걸면 교차 오염은 줄일 수 있어도 처리량과 지연이 나빠진다.
## 실습과 해설
두 요청의 고객 번호가 다른 상황을 장벽으로 교차 실행한다. 반환 결과와 실제 클라이언트에 전달된 ID가 요청별로 일치해야 한다. 순차 실행만으로는 문제를 발견하기 어렵다. 면접에서는 스코프의 정의와 요청 데이터 소유권을 연결하고, 인증 주체에서 얻은 고객 접근 권한도 별도로 검증해야 한다고 설명한다.
?? 이 사례의 우선 수정은?
+ 고객 번호를 공유 필드에서 제거하고 요청별 인자로 전달
- 싱글턴 빈 이름만 변경
- 모든 요청의 고객 번호를 동일하게 설정
- 응답에서 고객 번호만 숨김
!! 공유 가변 요청 상태가 교차 오염의 원인이므로 데이터 소유권을 요청 경계로 옮긴다.

@@ spring-proxy|프록시와 자기 호출의 트랜잭션 경계|기초|proxy
## 상황과 원리
서비스의 public 저장 메서드에 Transactional을 붙였지만 같은 객체의 다른 메서드가 this.save를 호출할 때 롤백이 안 된다. 기본 프록시 방식에서 조언은 프록시를 통과하는 호출에 적용된다. 애너테이션의 존재와 실제 호출 경로를 함께 확인해야 한다. AspectJ 등 다른 방식의 동작을 기본 프록시와 혼동하지 않는다.
## 판단 자료
```text
경로 A: Controller -> Service 프록시 -> save
경로 B: Service.target.run -> this.save
save: 상태 변경 뒤 예외 발생
```
## 수정과 영향
업무 트랜잭션의 시작점을 외부 진입 서비스로 이동하거나 책임이 다른 저장 작업을 별도 빈으로 분리한다. 자기 프록시 주입으로 우회하기 전에 서비스 책임이 적절한지 검토한다. 테스트에서 서비스 객체를 직접 new로 생성하면 Spring 프록시를 검증하지 못한다. 실제 빈과 DB를 사용해 상태·이력의 원자성을 확인한다.
## 실습과 해설
두 호출 경로에서 동일한 실패를 주입하고 커밋 이후 DB 상태를 새 트랜잭션으로 읽는다. 테스트 자체의 롤백 때문에 성공처럼 보이지 않게 한다. 체크 예외의 롤백 규칙과 같은 객체 호출 문제는 별개의 축이다. 면접에서는 ‘애너테이션이 안 먹었다’ 대신 프록시 진입 여부와 예외 전파 근거를 설명한다.
?? 기본 프록시 방식의 자기 호출 문제를 검증할 때 필요한 것은?
+ 실제 Spring 빈의 호출 경로와 커밋 이후 DB 상태 확인
- 애너테이션 문자열의 존재 여부만 확인
- 서비스 객체를 new로 만들고 프록시 동작을 단정
- 테스트가 끝나면 항상 롤백되니 저장 결과 생략
!! 적용 여부는 실제 프록시 경계와 트랜잭션 결과로 확인해야 한다.

@@ spring-propagation|REQUIRED·REQUIRES_NEW와 연결 풀|심화|propagation
## 상황과 원리
승인 작업 안에서 감사 기록을 REQUIRES_NEW로 저장했다. 감사 기록을 독립 커밋하려는 의도와 실제 자원 비용을 함께 검토해야 한다. REQUIRED는 기존 트랜잭션에 참여할 수 있고, REQUIRES_NEW는 외부 트랜잭션을 중단하고 독립 트랜잭션을 만든다. 일반적인 JDBC 환경에서는 추가 연결이 필요할 수 있다.
## 판단 자료
```text
동시 승인 요청 5개, 풀 크기 5
각 외부 트랜잭션이 연결 1개 보유
모두 내부 REQUIRES_NEW 연결을 기다림
```
## 수정과 영향
내부 독립 커밋이 정말 필요한지 먼저 정한다. 성공 감사와 실패 감사의 의미가 같지 않다. 외부 승인이 롤백돼도 남는 기록은 ‘승인 완료’라고 쓰면 안 된다. 풀 확대만으로 해결하기 전에 긴 외부 트랜잭션, 중첩 구조, 비동기 이벤트 또는 outbox 대안을 비교한다. 내부 트랜잭션이 외부가 잡은 잠금을 기다리면 다른 대기 문제도 생길 수 있다.
## 실습과 해설
외부 성공/실패와 내부 성공/실패를 조합해 남아야 할 기록을 표로 정한다. 작은 풀로 부하를 걸고 대기·timeout을 관찰한다. REQUIRED 내부에서 rollback-only가 된 경우 외부가 예외를 잡아도 커밋이 실패할 수 있음을 별도 검증한다. 면접에서는 전파 옵션의 정의뿐 아니라 독립 커밋이 남기는 업무 사실과 자원 경합을 설명한다.
?? 위 조건에서 모든 내부 트랜잭션이 대기할 수 있는 이유는?
+ 외부가 연결을 모두 점유한 채 독립 트랜잭션용 연결을 추가로 요청해서
- REQUIRES_NEW가 외부 연결을 항상 공유해서
- 감사 테이블 이름이 길어서
- REQUIRED가 자동으로 모든 예외를 삼켜서
!! 전파 정책은 커밋 의미뿐 아니라 연결 풀과 잠금 사용에 영향을 준다.

@@ spring-optimistic|낙관적 잠금과 갱신 충돌 응답|실무|jpa
## 상황과 원리
관리자 두 명이 같은 고객 정보를 열고 각각 수정했다. 나중 저장이 앞선 변경을 덮어쓴다. 버전 조건을 둔 낙관적 잠금은 자신이 읽은 버전과 저장 시점 버전이 같은지 검사한다. 충돌을 막연히 재시도하면 사용자가 확인하지 않은 새 값 위에 이전 의도를 적용할 수 있다.
## 판단 자료
```text
A와 B가 version=7 읽음
A: 주소 수정, version=8 저장
B: 연락처 수정, version=7 조건 -> 갱신 0건
```
## 수정과 영향
버전 충돌은 최신 정보를 다시 확인하게 하는 응답으로 전달한다. 어떤 필드를 자동 병합할 수 있는지는 업무 계약에 따라 다르다. 승인 금액처럼 함께 판단한 값은 임의 병합하지 않는다. JPA Version 사용 시 버전 검사 시점이 flush/commit에 나타날 수 있으므로 예외를 변환하는 경계를 확인한다. ORM을 거치지 않는 직접 SQL 갱신도 버전 정책과 일치시켜야 한다.
## 실습과 해설
독립된 두 트랜잭션으로 같은 버전을 읽고 순서대로 저장한다. 성공 한 건, 충돌 한 건, 유지된 이전 변경을 검증한다. 단일 트랜잭션에서 두 번 호출하는 테스트는 경합을 재현하지 못한다. 면접에서는 충돌 빈도와 비용에 따라 비관적 잠금과 비교하고 사용자 경험까지 설명한다.
?? 버전 충돌에 대해 무조건 이전 요청을 재시도하면 생길 수 있는 문제는?
+ 사용자가 보지 못한 최신 상태에 오래된 변경 의도를 적용할 수 있음
- 버전 숫자가 자동으로 과거로 돌아감
- 두 사용자가 반드시 동일한 값을 수정함
- 충돌 검사가 DB 읽기를 모두 금지함
!! 낙관적 충돌은 단순 전송 오류가 아니라 판단 기준이 바뀌었다는 신호일 수 있다.

@@ spring-jpa-nplusone|JPA N+1과 페이지 조회의 함정|실무|jpa
## 상황과 원리
기업 목록 20건을 조회했는데 SQL이 21번 실행된다. 지연 로딩된 관계를 반복 접근하며 추가 쿼리가 발생했을 수 있다. N+1은 특정 애너테이션 이름보다 실제 접근 패턴과 SQL 수로 확인한다. 모든 관계를 EAGER로 바꾸면 불필요한 조회와 중복 행이 늘 수 있다.
## 판단 자료
```text
기업 목록 1회
기업별 담당자 조회 20회
한 기업 담당자 3명, 목록 페이지 기준은 기업 20개
```
## 수정과 영향
화면이 필요한 필드만 DTO 조회하거나 적절한 fetch 전략·batch 조회를 검토한다. 컬렉션 fetch join에 페이지 제한을 결합하면 행 증식과 메모리 페이징 문제가 발생할 수 있으므로 ORM 버전과 실제 SQL을 확인한다. ID 페이지를 먼저 조회하고 필요한 관계를 별도 일괄 조회하는 대안은 쿼리 수가 늘어도 페이지 의미를 지키기 쉽다.
## 실습과 해설
관계 없음·한 개·여러 개인 기업을 섞어 페이지의 기업 수, SQL 수, 총 건수를 검증한다. 쿼리가 1번이라는 이유로 빠르다고 단정하지 말고 반환 행 수와 데이터 크기를 측정한다. 목록과 count 쿼리의 조건이 같은 집합을 세는지 확인한다. 면접에서는 lazy/eager 정의와 실제 화면의 데이터 요구를 연결한다.
?? 컬렉션 fetch join으로 모든 N+1을 해결하려 할 때 주의할 점은?
+ 관계 행 증식과 페이지 기준 기업 수의 불일치
- SQL은 적을수록 언제나 무조건 빠름
- EAGER는 모든 데이터를 캐시에 영구 저장
- 관계 없는 기업은 업무상 항상 삭제해도 됨
!! 쿼리 수와 페이지 의미, 반환량을 함께 검증해야 한다.

@@ spring-api-contract|HTTP 멱등성·검증·오류 응답 계약|기초|mvc
## 상황과 원리
GA 화면이 등록 응답을 받지 못해 같은 요청을 다시 보냈다. POST라는 이유만으로 무조건 새 건을 만들면 중복 등록이 된다. HTTP 메서드의 의미와 업무 요청의 멱등 키는 별도 설계 축이다. 입력 형식 오류, 권한 부족, 상태 충돌, 내부 장애를 서로 구분해야 호출자가 적절히 대응할 수 있다.
## 판단 자료
```text
키 K1 / 본문 A / 첫 호출: 저장 후 응답 유실
키 K1 / 본문 A / 재호출: 원래 결과 재사용
키 K1 / 본문 B / 재호출: 계약상 충돌
```
## 수정과 영향
사용자·업무 범위에 묶인 멱등 키와 본문 지문, 처리 상태·결과를 보관한다. 단순 메모리 캐시는 서버 재시작이나 다중 인스턴스에서 부족하다. 아직 처리 중인 요청에 대한 재호출 응답도 정한다. 오류 응답은 안정적인 코드와 사람이 읽는 설명을 구분하고 원문 SQL·스택을 노출하지 않는다.
## 실습과 해설
정상·동일 재전송·같은 키 다른 본문·동시 재전송을 실행한다. HTTP 상태뿐 아니라 실제 등록 건수와 반환된 리소스 ID를 확인한다. 키 만료 후 중복 방지 책임도 문서화한다. 면접에서는 중복 클릭 방지 UI와 서버·DB의 최종 중복 방지 역할을 구분한다.
?? 같은 키 K1에 다른 본문 B가 들어왔을 때 적절한 처리는?
+ 기존 요청과 충돌함을 알리고 새 업무 의도를 구분하도록 함
- 본문 차이를 무시하고 A를 B라고 응답
- 매번 새 행을 무조건 등록
- 화면 버튼만 비활성화하고 서버 검사를 제거
!! 같은 키를 서로 다른 업무에 재사용하면 결과 의미가 모호해진다.

@@ spring-authorization|인증과 객체 단위 인가|실무|security
## 상황과 원리
로그인한 설계사가 주소의 청약 ID를 바꾸어 다른 설계사의 청약을 조회했다. 인증은 누구인지 확인하는 것이고 인가는 그 사용자가 해당 자원에 어떤 행위를 할 수 있는지 판단하는 것이다. 메뉴 숨김이나 로그인 여부만으로 객체 접근을 보호하지 못한다.
## 판단 자료
```text
설계사 A 소유: proposal=101
설계사 B 소유: proposal=102
A가 GET /proposals/102 요청
요구: 별도 위임 권한이 없으면 거부
```
## 수정과 영향
서버가 인증된 주체로부터 소유 범위·역할·위임 관계를 확인한다. 요청 본문의 userId를 믿고 조회 조건을 만들지 않는다. 권한 검사를 Controller에만 두면 다른 진입 경로에서 빠질 수 있으므로 서비스/저장소 경계도 검토한다. 관리자 예외와 대리 업무는 명시적으로 모델링하고 감사 기록을 남긴다.
## 실습과 해설
자기 자료·남의 자료·삭제 자료·권한 변경 후 재접근·관리자 접근을 검증한다. 오류 메시지로 존재 여부를 과하게 드러내지 않는 정책도 검토한다. 조회뿐 아니라 수정·첨부 다운로드·검색 결과에도 같은 범위를 적용한다. 면접에서는 인증 필터 통과와 업무 객체 인가 성공을 구분해 설명한다.

@@ spring-session-csrf|세션 쿠키·CSRF·CORS의 역할|실무|csrf
## 상황과 원리
쿠키 기반 로그인 API에 CORS를 설정했으니 CSRF도 막힌다고 생각했다. CORS는 브라우저의 교차 출처 읽기 허용과 관련되고 CSRF는 브라우저가 자동 첨부하는 인증 정보를 악용한 요청을 다룬다. 두 기능의 역할은 다르다. 인증 방식과 사용 경로를 먼저 확인해야 한다.

## 수정과 영향
쿠키 인증 경로에는 프레임워크의 CSRF 보호와 토큰 전달, SameSite·Secure·HttpOnly 설정을 함께 검토한다. SameSite만으로 모든 상황을 설명하지 않는다. 토큰 기반 별도 클라이언트 경로와 브라우저 세션 경로의 보안 정책이 다르면 명시적으로 구분한다. 개발에서 편리하다는 이유로 보호를 전역 해제하지 않는다.

?? CORS 설정만으로 쿠키 기반 CSRF 보호가 끝났다고 볼 수 없는 이유는?
+ 교차 출처 응답 읽기 정책과 인증 쿠키를 이용한 상태 변경 요청의 정당성은 다르기 때문
- HttpOnly가 쿠키 전송 자체를 금지하기 때문
- 로그인한 요청에는 위조 가능성이 없기 때문
- POST는 브라우저에서 실행할 수 없기 때문
!! 요청이 보내지고 처리되는 문제와 브라우저가 응답을 읽는 문제를 구분해야 한다.

기본값이 업무상 유효한지 확인하고 대용량 backfill은 잠금·부하·재시작을 고려한다. 이중 쓰기는 두 값 불일치 가능성을 만들므로 기준값과 검증 지표를 정한다. 파괴적 변경 뒤 이전 바이너리로 돌아가는 것이 가능한지 사전에 판단한다. 마이그레이션 파일을 이미 적용한 뒤 수정하면 환경별 이력이 달라질 수 있다.
## 실습과 해설
구/신 애플리케이션과 구/신 스키마 조합의 지원 범위를 표로 만든다. 누락 행 수, 제약 위반, 이전 호출자의 응답을 확인한다. 테스트 DB의 작은 데이터 성공만으로 운영 잠금 시간을 단정하지 않는다. 면접에서는 배포 순서와 되돌리기 조건, 데이터 보존 근거를 설명한다.
