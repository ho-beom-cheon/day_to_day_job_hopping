@@ algo-complexity|복잡도와 반복 DB 호출의 비용|기초|algorithms
## 상황과 원리
거래 n건을 대사하며 각 거래마다 다른 목록 m건을 처음부터 찾는다. 중첩 반복의 비교 횟수는 최악에 n×m에 비례한다. Big-O는 입력이 증가할 때 비용의 증가 형태를 설명하며 실제 밀리초를 직접 알려주지 않는다. 반복 안의 DB 호출·네트워크 비용도 별도로 계산해야 한다.
## 판단 자료
```text
n=10000, m=10000 -> 최악 약 1억 비교
대상 목록을 업무 키 Map으로 구축: 구축 O(m), 평균 조회 전체 O(n)
추가 메모리 O(m), 해시 품질과 중복 키 정책 필요
```
## 수정과 영향
업무 키가 유일하면 조회 자료구조를 먼저 구성한다. 중복이 정상이라면 Map의 단일 값으로 덮어쓰지 말고 그룹을 유지한다. 데이터가 메모리에 들어오지 않으면 DB 조인·정렬 병합·청크 처리를 비교한다. 연산량을 줄여도 원본 로딩이 병목일 수 있다.
## 실습과 해설
입력 크기를 두 배로 늘릴 때 비교 횟수와 메모리 변화가 어떻게 되는지 예측한다. 없는 키, 중복 키, 빈 목록을 추가한다. 직접 코드를 새로 작성하지 않고 두 의사코드의 반복 횟수와 실패 조건을 설명하는 연습이다. 면접에서는 평균·최악 복잡도와 실제 측정 비용을 구분한다.
?? Map 전처리로 중첩 검색을 바꿀 때 함께 확인할 것은?
+ 추가 메모리와 중복 업무 키의 보존 정책
- HashMap이면 모든 조건에서 최악 O(1)이라고 단정
- 같은 키는 업무 의미와 무관하게 버림
- DB에서 읽는 비용은 항상 0이라고 가정
!! 조회량 감소에는 메모리와 키 의미에 대한 대가가 따른다.

@@ algo-hash|해시 집합·맵과 중복의 의미|기초|hashmap
## 상황과 원리
코어에서 받은 이벤트를 Set에 넣었는데 같은 업무의 상태 변경 이벤트가 사라졌다. 중복을 제거하기 전에 이벤트 ID와 업무 ID를 구분해야 한다. 하나의 청약에 여러 정상 변경이 있을 수 있다. Map은 키 하나에 값을 연결하고 Set은 원소 존재 여부를 다룬다.
## 판단 자료
```text
E1: 청약 P1, version1, 접수
E2: 청약 P1, version2, 승인
E1 재전송: 같은 이벤트
업무 ID P1로 Set 구성 -> 정상 E2도 손실 가능
```
## 수정과 영향
전송 중복은 이벤트 ID로, 최신 상태는 업무 ID와 버전으로 판단한다. 해시 충돌은 equals 계약으로 구별해야 하고 가변 키를 넣지 않는다. 무한 이벤트 집합은 메모리가 증가하므로 보관 범위를 정한다. 오래된 ID를 제거하면 그 이후의 재전송을 어떻게 다룰지도 결정한다.
## 실습과 해설
위 입력의 기대 적용은 접수 한 번, 승인 한 번이다. 같은 업무의 다른 이벤트, 같은 이벤트 재전송, 낮은 버전 지연 도착을 구분해 표를 만든다. 면접에서는 Set을 썼다는 이름보다 무엇을 동일하다고 정의했는지 설명한다.
?? 전송 중복 제거에 업무 ID만 사용하면 위험한 이유는?
+ 같은 업무의 정상적인 후속 상태 변경까지 제거할 수 있어서
- 모든 이벤트 ID는 업무 ID와 항상 같아서
- Set은 중복을 허용하지 않는 대신 순서를 항상 보장해서
- 버전이 있으면 재전송이 절대 발생하지 않아서
!! 이벤트 정체성과 업무 정체성은 다르다.

@@ algo-binary|이진 탐색의 경계와 단조 조건|기초|binary
## 상황과 원리
정렬된 거래 시각에서 기준 시각 이상인 첫 행을 찾는다. 이진 탐색은 비교 결과에 따라 탐색 구간을 절반으로 줄인다. 입력이 정렬되어 있거나 참/거짓 판정이 한 방향으로 바뀌는 단조 조건이 필요하다. 같은 값이 여러 개면 아무 일치값과 첫 일치값은 다른 요구다.
## 판단 자료
```text
시각 값 [1,3,3,3,8], 기준 3 -> 첫 위치 1 (0부터 시작)
기준 9 -> 위치 5, 즉 원소 없음
구간 [lo,hi), 중간 값 >= 기준이면 hi=mid
```
## 수정과 영향
찾는 경계를 lower bound인지 upper bound인지 명시한다. 종료 때 lo가 배열 길이일 수 있으므로 바로 접근하지 않는다. mid 계산과 구간 축소가 항상 진행되는지 확인한다. 정렬되지 않은 데이터에 이진 탐색을 적용하면 빠르게 틀린 답을 낼 수 있다.
## 실습과 해설
빈 배열, 전부 같은 값, 맨 앞/뒤 경계, 없는 값을 손으로 추적한다. 각 반복의 lo/hi/mid를 표로 적어 구간 길이가 줄어드는지 확인한다. 면접에서는 코드를 외우기보다 ‘정답이 아직 이 구간에 있다’는 불변식을 설명한다.
?? 기준 9를 찾았을 때 위치 5를 반환하면 필요한 처리는?
+ 배열 길이와 같으므로 해당 조건을 만족하는 원소가 없다고 처리
- 마지막 원소 8을 조건 충족으로 간주
- 무조건 인덱스 5를 읽기
- 정렬을 해제하고 같은 탐색을 반복
!! 경계 탐색은 유효 원소 위치 밖의 삽입 위치를 반환할 수 있다.

@@ algo-two-pointer|두 포인터와 중복 조합|실무|algorithms
## 상황과 원리
정렬된 금액 목록에서 합계가 목표인 두 항목을 찾는다. 양끝 포인터를 두고 합이 작으면 왼쪽, 크면 오른쪽을 이동할 수 있다. 정렬된 값이라는 조건이 이동 방향의 근거다. 같은 항목을 두 번 사용할 수 있는지, 같은 값의 서로 다른 항목은 허용하는지 먼저 정한다.
## 판단 자료
```text
값 [1,2,2,4,7], 목표 4
정답: 서로 다른 두 2의 인덱스
같은 인덱스 재사용 금지, 조건 left < right
```
## 수정과 영향
값 쌍 한 개만 찾는지 모든 인덱스 쌍을 세는지에 따라 중복 처리가 다르다. 정렬은 원래 인덱스를 바꾸므로 거래 식별자가 필요하면 함께 보관한다. 정렬 비용 O(n log n)과 탐색 O(n)을 분리해 설명한다. 입력이 이미 정렬되었는지도 확인한다.
## 실습과 해설
정답 없음, 두 원소, 같은 값 다수, 음수 포함 입력을 추적한다. 정렬된 배열의 양끝 합 이동과 음수의 존재는 양립할 수 있지만, 모든 두 포인터 문제에 같은 규칙이 적용되지는 않는다. 면접에서는 이동으로 버리는 후보가 왜 정답일 수 없는지 설명한다.
?? 목표 4에서 값 2가 한 번만 있을 때 같은 원소를 두 번 쓰지 않으려면?
+ left < right를 유지하고 서로 다른 인덱스를 선택
- left <= right면 항상 안전하다고 가정
- 값이 같으면 항상 같은 거래라고 간주
- 정렬하면 거래 ID가 자동 보존된다고 가정
!! 값의 동등성과 원소의 정체성을 구분해야 한다.

@@ algo-window|슬라이딩 윈도와 음수 반례|실무|algorithms
## 상황과 원리
연속된 거래 구간의 합이 한도 이상인 가장 짧은 구간을 찾는다. 모든 금액이 양수라면 오른쪽을 늘릴 때 합이 커지고 왼쪽을 줄일 때 합이 작아지는 성질을 이용할 수 있다. 음수 취소 거래가 들어오면 이 단조성이 깨진다.
## 판단 자료
```text
입력 [1,-1,5], 목표 5
단순 양수 전용 방식은 전체 길이 3을 답으로 남길 수 있음
실제 최소 구간은 [5], 길이 1
```
## 수정과 영향
입력 제약에 음수가 있는지 먼저 확인한다. 양수 전용 해법을 금융 데이터에 그대로 적용하지 않는다. 일반 정수에서는 누적합과 적절한 자료구조를 검토하며, 더 복잡한 해법이 필요하면 작은 완전 탐색을 정답 기준으로 사용해 비교한다. 시간 복잡도보다 가정의 성립이 먼저다.
## 실습과 해설
위 반례에서 전체 합 5가 된 후 왼쪽 1을 제거하면 4가 되어 더 줄이지 못하는 과정을 적는다. 다음 -1을 제거하면 5가 되지만 단순 규칙은 그 기회를 놓친다. 면접에서는 알고리즘을 바꿔야 하는 근거를 반례로 설명한다.
?? 양수 전용 윈도를 음수 포함 입력에 그대로 쓰면 안 되는 이유는?
+ 구간 확장·축소에 따른 합의 단조성이 깨지기 때문
- 음수는 어떤 알고리즘으로도 처리할 수 없기 때문
- 연속 구간은 항상 전체 배열이기 때문
- 정렬하면 연속 구간 의미가 보존되기 때문
!! 정렬은 원래 연속 구간 문제를 바꾸며 입력 가정을 검증해야 한다.

@@ algo-prefix|누적합과 구간 인덱스|기초|algorithms
## 상황과 원리
일별 거래 합계를 여러 기간에 대해 반복 계산한다. 매번 구간을 순회하면 질의 수가 많을 때 비용이 커진다. 누적합 P를 P[0]=0, P[i+1]=P[i]+a[i]로 만들면 반열린 구간 [l,r)의 합은 P[r]-P[l]이다.
## 판단 자료
```text
a=[10,20,-5,7]
P=[0,10,30,25,32]
[1,3) 합=25-10=15
```
## 수정과 영향
전처리 O(n), 구간 질의 O(1), 추가 공간 O(n)이다. 입력이 자주 변경되면 뒤쪽 누적합을 다시 계산하는 비용이 생기므로 갱신 빈도를 고려한다. 합계 타입은 큰 금액 누적에서 넘침이 없는지 확인한다. 시각 범위를 배열 인덱스로 바꾸는 기준도 필요하다.
## 실습과 해설
빈 구간 [2,2), 전체 구간 [0,4), 마지막 원소 [3,4)를 계산한다. 각각 0,32,7이다. 양끝 포함 구간과 반열린 구간을 섞으면 한 행이 빠지거나 더해진다. 면접에서는 공식을 외우기보다 경계 앞 누적값을 빼는 의미와 데이터 변경 시 비용을 설명한다.
?? 위 배열의 [1,3) 구간 합은?
+ 15
- 25
- 32
- 27
!! a[1]+a[2]=20-5이며 P[3]-P[1]=25-10이다.

@@ algo-sort|정렬 비교자의 동률·오버플로|실무|comparator
## 상황과 원리
금액 내림차순 정렬에서 두 금액을 빼서 int로 변환했다. 큰 값에서는 오버플로로 비교 방향이 뒤집힐 수 있다. 비교자는 일관된 순서 관계를 표현해야 한다. 동률의 표시 순서를 안정적으로 유지할 업무 키도 정한다.
## 판단 자료
```text
금액: 큰 양수와 큰 음수
잘못된 비교: (int)(a.amount - b.amount)
후보: Long.compare 또는 BigDecimal.compareTo
동률: 발생 시각, 거래 ID 순으로 추가 비교
```
## 수정과 영향
타입에 맞는 비교 함수를 사용하고 정렬 중 비교에 쓰는 값을 변경하지 않는다. stable sort는 기존 동률 순서를 보존할 수 있지만 원본 순서 자체가 불안정하면 반복 결과가 달라진다. DB 정렬과 앱 정렬의 NULL·문자 비교 정책도 맞춘다.
## 실습과 해설
극단값, 동률 세 건, null 허용 여부, 이미 정렬된 입력을 확인한다. 비교자의 반대칭성과 추이성이 깨지는 예가 없는지 작은 집합으로 검토한다. 면접에서는 정렬 알고리즘 이름보다 비교 기준과 재현 가능한 순서가 필요한 이유를 설명한다.
?? 뺄셈 후 int 변환으로 비교하는 방식의 위험은?
+ 값 범위를 넘으며 비교 부호가 잘못될 수 있음
- 정렬은 언제나 원본의 모든 필드를 수정함
- 안정 정렬이면 비교 함수가 없어도 됨
- 동률은 거래 ID가 반드시 같음을 의미
!! 비교는 타입 범위를 보존하는 함수와 명시적인 동률 규칙으로 구성한다.

@@ algo-stack|스택으로 중첩 구조와 오류 위치 찾기|기초|deque
## 상황과 원리
조건식 괄호의 짝이 맞는지 검사한다. 최근에 열린 괄호가 먼저 닫혀야 하므로 스택이 적합하다. 열린 괄호의 종류와 위치를 보관하면 단순 참/거짓보다 정확한 오류 위치를 제공할 수 있다.
## 판단 자료
```text
정상: ([x])
오류: ([x)] -> ')'에서 스택 최상단 '['와 불일치
오류: )x -> 스택 비어 있음
오류: (x -> 종료 후 '(' 남음
```
## 수정과 영향
닫는 괄호를 볼 때 비어 있는지 먼저 확인하고 종류를 비교한다. 문자열 리터럴이나 이스케이프 안의 괄호를 셀지 문법 계약을 정한다. 단순 괄호 검사기는 전체 SQL·표현식 파서와 같지 않다. 입력 길이가 n이면 일반적인 단일 순회는 O(n), 중첩 깊이만큼 공간을 쓴다.
## 실습과 해설
위 입력의 각 문자에서 스택 상태를 적는다. 빈 입력, 아주 깊은 중첩, 인용문 속 괄호를 추가한다. 오류를 발견해도 모든 문법이 검증됐다고 말하지 않는다. 면접에서는 LIFO가 중첩 구조에 맞는 이유와 검증 범위의 한계를 설명한다.
?? '([x)]'가 실패하는 첫 핵심 조건은?
+ 닫는 ')'가 최근 열린 '['와 종류가 다름
- 열린 괄호 총수와 닫힌 괄호 총수가 같음
- 문자열 길이가 홀수임
- 입력에 영문자가 있음

@@ algo-bfs|BFS·DFS와 방문 시점|실무|deque
## 상황과 원리
배치 실패로 영향을 받는 후속 작업을 찾는다. 정점은 작업, 간선은 결과 의존 관계다. BFS는 큐로 가까운 연결부터, DFS는 한 경로를 깊게 탐색한다. 가중치 없는 그래프에서 BFS는 간선 수 기준 최단 거리를 구할 수 있지만 임의 가중치 비용의 최단 경로를 보장하지 않는다.
## 판단 자료
```text
A->B, A->C, B->D, C->D, D->A
A의 영향 후보 B,C,D
방문 표시는 큐에 넣을 때 수행 -> D 중복 삽입 방지
```
## 수정과 영향
간선 방향과 시작 정점 포함 여부를 명시한다. 순환이 있어도 방문 집합으로 종료되게 한다. DFS 재귀는 깊은 그래프에서 호출 스택 문제가 생길 수 있다. 메모리 전체 적재와 정점별 DB 조회의 비용도 비교한다. 탐색 결과를 바로 실행 순서로 사용하지 않는다.
## 실습과 해설
다이아몬드·순환·미연결·없는 시작 ID를 손으로 추적한다. 각 정점과 간선을 제한된 횟수로 다루면 인접 리스트 기준 O(V+E)다. 면접에서는 탐색 후보 식별과 업무 재처리 승인·실행 순서의 차이를 설명한다.
?? BFS 방문 표시를 큐에 넣을 때 하는 이유는?
+ 여러 부모가 같은 정점을 가리켜도 중복 삽입을 줄이기 위해
- 모든 그래프가 트리이기 때문에
- 가중치가 있어도 항상 최단 비용이 되기 때문에
- 방문 집합이 업무 실행 승인도 대신하기 때문에
!! 방문 상태는 탐색 중복과 순환을 통제하며 업무 실행 규칙은 별도다.

@@ algo-topological|위상 정렬과 순환 의존성 검출|실무|algorithms
## 상황과 원리
원장 집계가 끝나야 대사, 대사가 끝나야 보고서를 만들 수 있다. 의존 작업을 실행 순서로 나열하려면 방향 그래프의 선행 조건을 만족해야 한다. 진입 차수가 0인 정점부터 제거하는 위상 정렬은 DAG에서 가능한 순서를 만든다.
## 판단 자료
```text
A->C, B->C, C->D
가능: A,B,C,D 또는 B,A,C,D
D->A 추가 -> 일부 정점이 끝까지 남아 순환 검출
```
## 수정과 영향
진입 차수 0 후보가 여럿이면 업무 우선순위와 안정적인 동률 규칙을 정한다. 탐색 종료 후 처리한 정점 수가 전체와 같은지 확인한다. 부분 목록만 반환하고 성공 처리하면 순환에 묶인 작업이 누락된다. 작업 실패와 그래프 순환은 다른 오류다.
## 실습과 해설
각 정점을 제거할 때 남은 진입 차수를 표로 적는다. 미연결 작업도 포함하고 중복 간선 입력의 처리 정책을 검증한다. 면접에서는 하나의 정답 순서만 있는 것이 아니라 제약을 만족하는 여러 순서가 가능하다고 설명한다. 실제 병렬 실행에는 실행 상태와 재시도 규칙이 추가로 필요하다.
?? 처리 정점 수가 전체보다 작은데 준비 큐가 비었다면 의심할 것은?
+ 남은 부분의 순환 의존성
- 위상 정렬이 항상 모든 방향 그래프에서 가능함
- 알파벳 순으로 정렬하면 의존성이 자동 충족됨
- 남은 작업은 중요하지 않으므로 삭제 가능함
!! DAG 조건을 만족하지 않으면 전체 위상 순서를 만들 수 없다.

@@ algo-heap|우선순위 큐의 Top-K와 변경 키|실무|heap
## 상황과 원리
수많은 작업 중 가장 빠른 마감 작업을 반복 선택한다. 우선순위 큐는 매번 전체 정렬하지 않고 우선 원소를 꺼내는 데 적합하다. 큐 안 객체의 우선순위 필드를 바꾼다고 내부 순서가 자동 재구성된다고 가정하지 않는다.
## 판단 자료
```text
A deadline=10, B deadline=20
삽입 후 B deadline=5로 객체만 변경
올바른 우선순서를 원하면 제거·재삽입 또는 새 버전 항목 정책 필요
```
## 수정과 영향
키를 불변으로 두고 변경 시 새 항목을 추가한 뒤 오래된 버전을 건너뛰는 방법을 고려한다. 취소된 작업을 꺼낼 때 현재 상태도 검증한다. Top-K는 크기 K의 반대 방향 heap을 유지하는 방식으로 O(n log K)를 노릴 수 있다. 동률은 업무 등급·생성 순번 등으로 정한다.
## 실습과 해설
동률·우선순위 변경·취소·빈 큐·K가 입력보다 큰 경우를 확인한다. 반복자는 우선순위 순서라고 가정하지 말고 실제 poll 순서를 비교한다. 면접에서는 heap을 선택한 삽입/조회 비율과 변경 항목 처리 방법을 설명한다.
?? 큐 안 객체의 deadline만 바꾸는 방식의 문제는?
+ 내부 heap 순서가 변경된 키에 맞춰 자동 복구된다고 보장할 수 없음
- 우선순위 큐에는 동률이 들어갈 수 없음
- 반복자가 항상 정렬된 전체 목록을 반환함
- poll은 항상 가장 최근 삽입 항목을 반환함
!! 자료구조의 정렬 키 변경은 명시적인 재구성 정책이 필요하다.

@@ algo-dijkstra|다익스트라와 음수 간선의 제약|심화|algorithms
## 상황과 원리
서비스 간 이동 비용이 다른 그래프에서 최소 비용 경로를 찾는다. 다익스트라는 비음수 간선 조건에서 현재 가장 짧은 후보를 확정해 나갈 수 있다. BFS의 간선 수와 비용 합은 다른 기준이다. 음수 가중치가 있으면 확정한 거리가 나중에 더 작아질 수 있다.
## 판단 자료
```text
S->A 비용 2, S->B 비용 5, B->A 비용 -10

가중치 제약을 확인하고 음수가 있으면 다른 알고리즘과 음수 순환 정책을 검토한다. 비음수 조건에서 heap을 쓸 때 오래된 거리 항목을 건너뛰고 합산 타입의 범위도 확인한다. 경로가 없는 상태를 0 비용으로 표현하지 않는다.
## 실습과 해설
비음수 작은 그래프는 손으로 모든 경로를 비교해 검산한다. 없는 경로, 0 비용 간선, 여러 최단 경로, 위 음수 반례를 검증한다. 면접에서는 이름만 말하지 말고 어떤 입력 제약 때문에 선택했는지 설명한다. 최단 경로가 업무 승인이나 네트워크 가용성을 보장하는 것은 아니다.
?? 위 음수 간선 사례가 보여주는 것은?
+ 다익스트라의 비음수 가중치 전제를 확인해야 함
- BFS가 모든 비용 그래프의 최단 비용을 보장함
- 음수 간선이 있어도 확정 순서는 항상 안전함
- 도달 불가는 0 비용과 같음
!! 알고리즘의 정당성은 입력 제약에 의존한다.

dp[0]=0, dp[x]=min(dp[x-c]+1), 가능한 c만 사용
```

도달 불가능을 큰 값이나 별도 상태로 두고 넘침 없이 처리한다. 각 단위를 무한히 쓸 수 있는지 한 번만 쓸 수 있는지에 따라 점화식과 반복 순서가 달라진다. 금액 크기 자체에 비례하는 해법은 입력 숫자가 매우 크면 실행 불가능할 수 있다.

- 4개
- 만들 수 없음

@@ algo-union-find|Union-Find와 연결 관계의 한계|심화|algorithms
## 상황과 원리
고객 식별자 간 연결 정보를 합쳐 같은 그룹인지 빠르게 확인하려 한다. Union-Find는 집합 병합과 대표자 조회에 적합하다. 연결되어 있다는 사실과 동일 인물이라는 업무 판정은 다르므로 알고리즘 결과를 곧바로 고객 통합 승인으로 쓰지 않는다.
## 판단 자료
```text
연결 A-B, B-C -> A와 C 같은 연결 집합
D는 별도 집합
B-C 관계를 취소하면 단순 Union-Find만으로 집합을 쉽게 분리할 수 없음
```
## 수정과 영향
경로 압축과 rank/size 기반 병합으로 반복 조회 비용을 줄인다. 관계 삭제와 과거 시점 조회가 필요하면 재구축이나 다른 자료구조를 검토한다. 대표 노드는 업무상 대표 고객과 다를 수 있다. 연결 근거와 병합 이력을 별도로 보관한다.
## 실습과 해설
같은 연결 중복 입력, 이미 같은 집합 병합, 별도 정점, 관계 취소 요청을 검증한다. 연결 여부의 기대값과 실제 고객 통합 승인 결과를 분리한다. 면접에서는 자료구조가 지원하는 연산과 지원하지 않는 연산을 함께 설명하고, 빠른 조회 때문에 삭제 요구를 숨기지 않는다.
?? 단순 Union-Find를 선택할 때 특히 확인할 추가 요구는?
+ 관계 삭제로 집합을 다시 분리해야 하는지
- 대표 노드가 항상 업무상 대표 고객인지
- 연결이면 법적으로 같은 사람인지
- 병합하면 근거 이력이 필요 없는지
!! Union-Find는 병합·연결 조회에 강하지만 삭제·분리는 별도 설계가 필요하다.
