## 핵심 개념
- 고정 길이 전문은 필드 위치와 길이를 **바이트** 단위로 약속한다. Java `String.length()`는 UTF-16 code unit 수라서 바이트 길이와 다르다. 길이 계산·자르기·채우기는 계약된 인코딩으로 변환한 바이트 배열 기준이어야 한다.
- 인코딩마다 한글 한 글자의 바이트 수가 다르다. UTF-8은 U+0800~U+FFFF 범위 문자를 3바이트로 표현하므로 한글 음절은 3바이트다. 한국어 레거시 연계에서 흔한 EUC-KR·MS949(Java NIO 이름 `x-windows-949`)는 한글 음절을 2바이트로 표현한다. 같은 "홍길동"도 인코딩에 따라 필드 길이가 달라진다.
- 바이트 단위로 자르면 멀티바이트 문자 중간이 잘릴 수 있다. 이런 바이트를 `new String(bytes, charset)`이나 `getBytes(charset)`로 변환하면 오류 없이 대체 문자로 바뀐다. 잘못된 입력을 감지하려면 `CharsetDecoder`를 `CodingErrorAction.REPORT`로 설정해 직접 써야 한다.
- 인자 없는 `getBytes()`·`new String(byte[])`는 기본 charset을 쓰고, 기본 charset으로 표현할 수 없을 때 동작은 명세되지 않았다. JDK 18부터 기본 charset이 UTF-8로 바뀌어(JEP 400), JDK 업그레이드만으로 전문 바이트가 달라질 수 있다. 연계 코드는 항상 charset을 명시한다.
- 패딩 규칙(문자는 우측 공백, 숫자는 좌측 0 등), 부호·소수점 표현, 날짜 형식은 기관마다 다른 **계약 사항**이다. 일반 상식으로 가정하지 말고 전문 명세서와 상대 기관 확인으로 정한다.
- 하위 호환은 "기존 상대방이 아무것도 바꾸지 않아도 계속 동작하는가"로 판단한다. 고정 길이 전문은 중간 필드 추가·길이 변경이 뒤 필드 위치를 모두 바꾸므로 사실상 비호환 변경이다. 전문 버전·길이 필드, 예비(filler) 영역 사용, 신·구 전문 병행 기간 같은 장치를 계약으로 정해야 한다.
- JSON 같은 구조형 API는 필드 추가가 상대적으로 쉽지만, 받는 쪽이 모르는 필드를 거부하도록 설정돼 있으면 추가도 장애가 된다. 필드 의미 변경·필수화·타입 변경·삭제는 비호환이다.

## 판단 기준
- [K1] 전문 길이·위치를 바이트 기준으로 계산하는지, 문자 수(`length()`, `substring`) 기준으로 계산하는지 구분해 잘못된 지점을 찾는다.
- [K2] 송수신 양쪽의 인코딩을 명시적으로 확인하고, charset 미지정 API(`getBytes()`, `new String(byte[])`)와 기본 charset 변경(JDK 18) 위험을 지적한다.
- [K3] 바이트 단위 자르기에서 멀티바이트 문자가 잘리는 경계와 대체 문자로 조용히 깨지는 동작을 다루고, 감지 방법(REPORT)이나 문자 경계 기준 자르기를 제시한다.
- [K4] 패딩·숫자·부호·날짜 표현을 명세서 기준으로 확인하고, 명세에 없는 부분은 상대 기관 확인 사항으로 남긴다.
- [K5] 필드 추가·변경이 기존 상대방에게 호환인지 비호환인지 판정한다(위치 이동, 길이 변경, 의미 변경, 필수화).
- [K6] 비호환 변경의 전환 전략을 제시한다: 전문 버전 구분, filler 활용, 신·구 병행 기간, 양측 배포 순서, 되돌리기 방법.
- [K7] 경계값 테스트를 설계한다: 최대 길이 한글·영문 혼합, 정확히 경계에서 잘리는 멀티바이트 문자, 빈 값·공백, 특수문자, 숫자 필드 최대값·음수.
- [K8] 운영 검증 수단을 둔다: 송수신 전문 원문(바이트 hex) 로그와 개인정보 마스킹, 상대 기관과의 테스트 전문 교환, 전환 후 대사.

## 흔한 실수와 반례
- `String.format("%-20s", name)`으로 20자리를 맞춘다 → 문자 수 기준이라 한글이 들어가면 바이트 길이가 20을 넘어 뒤 필드가 모두 밀린다 → 계약 인코딩으로 변환한 바이트 길이로 채우고 자른다.
- `name.getBytes()`로 변환한다 → 기본 charset을 쓰므로 서버 환경·JDK 버전에 따라 바이트가 달라진다. JDK 18부터 기본값이 UTF-8이다 → `getBytes(Charset.forName("x-windows-949"))`처럼 계약 인코딩을 명시한다.
- 바이트 배열을 고정 길이로 자른 뒤 `new String`으로 되돌려 확인한다 → 잘린 멀티바이트 문자는 예외 없이 대체 문자로 바뀌어 문제가 숨는다 → 문자 경계에서 자르거나 REPORT 디코더로 감지한다.
- 수신 전문 끝에 필드를 추가하면 무조건 호환이라고 본다 → 상대가 전문 전체 길이를 검증하면 길이 불일치로 거절된다 → 상대 기관의 길이 검증 방식을 확인하고 버전·길이 필드 규칙을 계약한다.
- 중간에 필드를 끼워 넣고 양쪽을 같은 날 배포하면 된다고 본다 → 배포 시각 차이 동안 신·구 전문이 섞이고, 되돌릴 때도 같은 문제가 생긴다 → 버전 구분 병행 처리나 filler 사용으로 단계 전환한다.
- 명세서에 없는 숫자 필드 음수 표현을 '-' 접두로 가정한다 → 기관마다 부호 표현이 달라 금액이 틀리게 해석될 수 있다 → 명세 확인 전까지 확인 필요 항목으로 남기고 테스트 전문으로 검증한다.
- JSON 응답에 필드를 추가했으니 하위 호환이라고 단정한다 → 수신 측이 모르는 필드를 오류로 처리하면 장애가 난다 → 수신 측 역직렬화 설정과 계약 문서를 확인한다.

## 수준별 기대 답변
### 수준 2
- 코드에서 문자 수 기준 패딩이나 charset 미지정 같은 문제 하나를 찾아 "한글이 들어가면 전문 길이가 틀어집니다"까지 말한다.
### 수준 3
- 인코딩별 바이트 수, 자르기 경계, 기본 charset 문제를 연결해 원인과 영향을 설명하고, 바이트 기준 처리로 고치는 방향과 경계값 테스트를 제시한다.
- 필드 변경이 호환인지 판정하고 근거를 댄다.
### 수준 4
- 상대 기관이 여럿이고 배포 시점이 다른 상황에서 버전 병행·전환 순서·되돌리기·전환 후 대사까지 설계한다.
- "상대 기관이 일정상 못 바꾸면?", "전환 중 전문이 섞이면?" 같은 꼬리질문에 답한다.

## 꼬리질문 후보
- `String.length()`와 전문 바이트 길이가 다른 이유를 설명해 주세요. 이모지가 들어오면요?
- 한글 이름 필드를 바이트로 자를 때 글자 중간이 잘리면 무슨 일이 생기나요? 왜 예외가 안 나죠?
- 서버 JDK를 17에서 21로 올렸더니 전문이 깨졌습니다. 어디를 의심하겠어요?
- 전문 끝에 필드를 추가하는 건 호환인가요? 어떤 조건에서 아닌가요?
- 상대 기관이 3곳이고 반영일이 다르면 전환을 어떻게 하겠어요?
- 전문 원문 로그를 남기면 개인정보 문제는 어떻게 하죠?
- C로 된 기존 연계 모듈을 Java로 전환할 때 바이트 단위 동작이 같은지 어떻게 검증하겠어요?
- 숫자 필드에 소수점 금액이 들어가야 하면 명세에서 무엇을 확인하겠어요?

## 시나리오 재료
- CB(신용정보) 조회 요청 전문의 고객명 필드(20바이트)에 긴 한글 이름이 들어가 뒤 필드인 주민번호 영역이 밀린 사례.
- 기존 C 모듈을 Java로 전환하면서 `getBytes()` 기본 charset을 써 개발 PC와 운영 서버의 전문 길이가 달랐던 사례.
- JDK 업그레이드 후 대외 기관 응답 전문의 한글 상호명이 깨져 보이는 사례.
- 보험 GA 연계 API에 '모집인 등급' 필드를 추가하자 한 제휴사 시스템이 요청을 거절한 사례.
- 카드 승인 전문 중간에 필드를 추가하는 개정 요청을 받고 전환 계획을 세워야 하는 사례.
- 은행 대외계 전문의 금액 필드 부호·소수점 표현을 두고 명세서와 실제 수신 전문이 다른 사례.
- 고정 길이 전문 30바이트 경계에 한글이 걸려 마지막 글자가 깨진 채 저장된 사례.
- 마이데이터 API 응답의 필드 의미가 바뀌었는데(단위 변경) 필드명은 그대로인 사례.

## 공식 출처
- [Java SE 21 API — String](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/lang/String.html) — length()는 UTF-16 code unit 수, getBytes()·new String(byte[]) 기본 charset 사용과 표현 불가 시 미명세, charset 지정 변환은 대체 문자로 바꿈
- [Java SE 21 API — CharsetDecoder](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/nio/charset/CharsetDecoder.html) — REPORT·REPLACE 동작, REPORT 시 MalformedInputException
- [Java SE 21 — Supported Encodings](https://docs.oracle.com/en/java/javase/21/intl/supported-encodings.html) — EUC-KR, x-windows-949(java.io 이름 MS949), UTF-8의 정식 이름과 별칭
- [JEP 400: UTF-8 by Default](https://openjdk.org/jeps/400) — JDK 18부터 기본 charset UTF-8, file.encoding=COMPAT로 이전 동작 복원, 아시아 로캘 Windows 사용자 영향
- [RFC 3629 UTF-8](https://www.rfc-editor.org/rfc/rfc3629.html) — U+0800~U+FFFF 문자는 3옥텟으로 인코딩
