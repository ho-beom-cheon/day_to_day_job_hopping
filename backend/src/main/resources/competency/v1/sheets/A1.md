## 핵심 개념
- Spring 선언적 트랜잭션은 기본이 프록시 모드다. 프록시를 거쳐 들어온 외부 호출만 가로채므로, 같은 객체 안에서 `this.method()`로 부르는 self-invocation은 대상 메서드에 `@Transactional`이 있어도 새 트랜잭션 설정이 적용되지 않는다.
- `@Transactional`은 보통 public 메서드에 쓴다. Spring 6.0부터 클래스 기반 프록시에서는 protected·package 가시성 메서드도 기본으로 트랜잭션이 적용되지만, 인터페이스 기반 프록시에서는 인터페이스에 정의된 public 메서드여야 한다.
- 기본 롤백 규칙: `RuntimeException`과 `Error`는 롤백, checked 예외는 롤백하지 않는다. `rollbackFor`로 바꿀 수 있고, 예외를 메서드 안에서 잡아 삼키면 인터셉터는 예외를 보지 못하므로 커밋된다.
- `REQUIRED`(기본)는 물리 트랜잭션 하나를 공유한다. 참여하는 내부 범위의 격리 수준·timeout·readOnly 설정은 무시된다. 내부 범위가 rollback-only로 표시하면 외부가 커밋을 시도할 때 `UnexpectedRollbackException`이 난다.
- `REQUIRES_NEW`는 항상 독립된 물리 트랜잭션을 연다. 외부 트랜잭션의 커넥션을 쥔 채 새 커넥션을 하나 더 얻으므로 풀 크기가 동시 스레드 수보다 충분히 크지 않으면 풀 고갈·교착이 날 수 있다.
- `NESTED`는 한 물리 트랜잭션 안의 savepoint로 동작하며 JDBC 리소스 트랜잭션(`DataSourceTransactionManager`)에서만 쓸 수 있다.
- `readOnly`는 트랜잭션 하위 시스템에 주는 최적화 힌트다. 쓰기 시도를 반드시 실패시키는 보장이 아니며, 실제 효과는 트랜잭션 매니저·드라이버·DB에 따라 다르다.
- 트랜잭션 경계는 "무엇이 함께 성공하거나 함께 실패해야 하는가"로 정한다. 경계가 넓으면 잠금·커넥션 점유 시간이 길어지고, 좁으면 부분 반영이 생긴다.

## 판단 기준
- [K1] self-invocation, private 메서드, 프록시를 거치지 않는 호출 경로 때문에 `@Transactional`이 기대대로 적용되지 않는 지점을 찾아낸다.
- [K2] 예외 종류(checked/unchecked)와 예외를 잡아 삼키는 코드가 커밋·롤백 결과를 어떻게 바꾸는지 판단한다.
- [K3] `REQUIRED` 참여 중 내부에서 rollback-only가 표시되면 외부 커밋 시 `UnexpectedRollbackException`이 난다는 것을 알고, 그 의도를 설명한다.
- [K4] 실패해도 남아야 하는 기록(실패 이력, 감사 로그)에 `REQUIRES_NEW`를 쓸지 판단하고, 커넥션 추가 점유와 풀 크기 영향을 함께 따진다.
- [K5] `readOnly`를 쓰기 차단 장치가 아니라 힌트로 보고, 참여 트랜잭션에서는 내부 readOnly 설정이 무시된다는 점을 반영한다.
- [K6] 업무 단위(함께 성공·실패해야 하는 변경)를 기준으로 트랜잭션 경계를 정하고, 외부 호출·대기 작업을 트랜잭션 밖으로 뺄지 판단한다.
- [K7] 수정안마다 검증 방법을 제시한다: 트랜잭션 로그(트랜잭션 매니저 DEBUG 로그), 통합 테스트에서 롤백 여부 확인, DB 반영 결과 확인.
- [K8] 구조 수정 대안(별도 빈 분리, 호출 위치 이동, `TransactionTemplate` 같은 프로그래밍 방식, AspectJ 모드)을 비교하고 선택 근거를 댄다.

## 흔한 실수와 반례
- 같은 클래스 안의 `@Transactional(propagation = REQUIRES_NEW)` 메서드를 `this`로 호출해 독립 커밋을 기대한다 → 프록시 모드에서는 가로채지 않아 외부 트랜잭션에 그대로 묶인다 → 별도 빈으로 분리하거나 프로그래밍 방식으로 경계를 연다.
- checked 예외(예: 업무 예외를 `Exception` 상속으로 정의)를 던지면 롤백될 것이라 생각한다 → 기본 규칙상 checked 예외는 롤백하지 않아 앞선 변경이 커밋된다 → `rollbackFor`를 지정하거나 예외 계층을 정리한다.
- 내부 서비스에서 예외를 catch하고 로그만 남긴 뒤 정상 반환한다 → 인터셉터가 예외를 보지 못해 부분 반영이 커밋된다. 반대로 내부 `REQUIRED` 메서드가 예외로 rollback-only를 표시한 뒤 외부가 그 예외를 삼키면 외부 커밋 시 `UnexpectedRollbackException`이 난다 → 어느 쪽인지 호출 구조로 구분해서 설명해야 한다.
- `@Transactional(readOnly = true)`를 붙였으니 조회 메서드에서 실수로 UPDATE해도 막힐 것이라 본다 → readOnly는 힌트이고 쓰기 실패를 보장하지 않는다 → 쓰기 차단이 필요하면 권한·구조로 막고, 실제 동작은 사용하는 환경에서 확인한다.
- 실패 이력 저장에 `REQUIRES_NEW`를 쓰면 무조건 안전하다고 본다 → 요청마다 커넥션을 2개 쥐어 동시 요청이 많으면 풀 고갈·교착 위험이 있다 → 풀 크기, 호출 빈도, 비동기 기록 대안을 함께 검토한다.
- 외부 API 호출을 트랜잭션 안에 두고 timeout만 늘린다 → 응답 대기 동안 커넥션과 잠금을 계속 점유한다 → 호출 전후로 상태를 나눠 기록하고 외부 호출은 트랜잭션 밖으로 빼는 방안을 비교한다.

## 수준별 기대 답변
### 수준 2
- 코드에서 self-invocation이나 checked 예외 때문에 트랜잭션이 기대와 다르게 동작하는 지점을 짚는다. "같은 클래스 내부 호출이라 REQUIRES_NEW가 적용되지 않습니다"까지 말한다.
### 수준 3
- 원인(프록시 동작, 롤백 규칙, 전파 속성)을 설명하고 수정안 2개 이상을 비교해 하나를 고른다.
- 수정 후 무엇이 커밋되고 무엇이 롤백되는지를 단계별로 설명하고, 트랜잭션 로그·통합 테스트로 확인하는 방법을 제시한다.
### 수준 4
- 커넥션 풀 크기, 동시 요청 수, 외부 호출 지연까지 고려해 경계를 설계한다.
- "그 상태에서 서버가 죽으면?", "이력 저장이 실패하면?" 같은 꼬리질문에 데이터가 어떤 상태로 남는지와 복구 방법으로 답한다.

## 꼬리질문 후보
- 같은 클래스 안에서 호출하면 왜 트랜잭션이 적용되지 않나요? 프록시가 어디에 있나요?
- 이 메서드를 별도 빈으로 뺐을 때 순환 참조나 책임 분리 문제는 없나요? 다른 방법은요?
- 내부 메서드가 예외를 던졌고 외부에서 잡았는데 왜 `UnexpectedRollbackException`이 나죠?
- `REQUIRES_NEW`를 쓰면 커넥션이 몇 개 필요한가요? 동시 요청 100건이면요?
- checked 예외를 던졌는데 데이터가 커밋됐습니다. 어디를 고치겠어요?
- `readOnly = true`는 정확히 무엇을 해 주나요? 쓰기를 막아 주나요?
- 외부 API 호출을 트랜잭션 안에 두면 어떤 문제가 생기나요? 밖으로 빼면 무엇이 새로 어려워지나요?
- 수정이 맞는지 운영 배포 전에 어떻게 확인하겠어요?

## 시나리오 재료
- 대출 신청 저장 후 같은 서비스 안의 `saveFailureHistory()`(REQUIRES_NEW)를 내부 호출해 실패 이력이 본 거래와 함께 롤백되는 사례.
- 이체 처리 중 한도 초과를 checked 예외 `LimitExceededException`으로 던졌는데 출금 원장 INSERT가 커밋된 사례.
- 카드 승인 서비스에서 포인트 적립 실패를 catch해 무시했는데 승인 응답 직전 `UnexpectedRollbackException`이 나는 사례.
- 보험 계약 변경 배치에서 건별 감사 로그를 REQUIRES_NEW로 남기다 피크 시간에 커넥션 풀 대기 시간이 급증한 사례.
- 고객 조회 API에 `readOnly = true`를 붙였는데 조회 이력 UPDATE가 그대로 반영된 사례.
- 신용정보 조회 결과 저장 트랜잭션 안에서 외부 CB 기관 호출이 지연돼 같은 테이블 갱신이 잠금 대기에 걸린 사례.
- MyBatis 매퍼 2개를 쓰는 서비스에서 한쪽 매퍼만 반영되고 다른 쪽은 롤백됐다는 운영 문의(호출 경로가 프록시를 거치지 않는 경우).
