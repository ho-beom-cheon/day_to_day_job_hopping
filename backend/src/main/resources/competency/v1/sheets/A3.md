## 핵심 개념
- 멱등(idempotent)은 같은 요청을 여러 번 보내도 서버에 의도된 효과가 한 번 보낸 것과 같다는 뜻이다. HTTP에서는 PUT, DELETE와 안전한 메서드(GET, HEAD, OPTIONS, TRACE)가 멱등으로 정의되고, POST는 멱등이 아니다. 로그 기록처럼 요청마다 남는 부수 효과는 멱등 판단 대상이 아니다.
- RFC 9110은 클라이언트가 비멱등 요청을 자동 재시도하지 않아야 하며(SHOULD NOT), 요청이 실제로 멱등이거나 원래 요청이 적용되지 않았음을 알 수 있을 때만 예외로 둔다. 타임아웃은 "실패"가 아니라 "결과 불명"이다.
- 금융 거래(이체, 승인, 지급)는 대부분 POST 성격이라 프로토콜이 멱등을 보장하지 않는다. 그래서 업무 수준에서 멱등 키(거래 고유번호, 요청 ID)를 정하고 서버가 중복을 판정해야 한다.
- IETF `Idempotency-Key` 헤더 초안(작성 중인 Internet-Draft)은 키가 유일해야 하고 다른 페이로드에 재사용하면 안 된다고 정한다. 같은 키에 다른 페이로드면 422, 원 요청 처리 중 재시도면 409를 제안하고, 처리 완료 후 재시도에는 원 결과와 일치하는 응답을 주도록 한다. 키 만료 정책은 서버가 정해 문서화한다.
- 중복 판정은 DB 유일 제약(unique key)으로 최종 보장한다. "SELECT로 없음 확인 후 INSERT"는 동시 요청 둘이 모두 통과할 수 있다. Oracle 유일 제약은 인덱스로 강제되며, NOT NULL이 없으면 NULL은 항상 유일 제약을 통과한다.
- 처리 상태(접수·처리 중·완료·실패)를 키와 함께 저장해야 "처리 중 재요청", "완료 후 재요청", "실패 후 재요청"을 다르게 응답할 수 있다.

## 판단 기준
- [K1] 이중 처리가 생기는 경로를 구체적으로 찾는다: 클라이언트·게이트웨이·프레임워크 자동 재시도, 사용자 재클릭, 배치 재실행, 메시지 재전달.
- [K2] 타임아웃을 실패로 단정하지 않고 "결과 불명"으로 다룬다. 재시도 전에 원 거래의 처리 여부를 조회하거나 멱등 키로 재요청한다.
- [K3] 멱등 키의 범위와 생성 주체를 정한다: 누가 만들고(요청자), 무엇과 묶이며(고객·채널·거래), 언제 만료되는지.
- [K4] 중복 판정을 유일 제약 같은 원자적 장치로 보장하고, check-then-insert 경쟁 조건을 지적한다.
- [K5] 같은 키·다른 내용(페이로드 지문 불일치)을 오류로 거절해 키 재사용으로 다른 거래가 묻히지 않게 한다.
- [K6] 상태별 응답을 설계한다: 처리 중 재요청(대기·충돌 응답), 완료 후 재요청(저장된 원 결과 반환), 실패 후 재요청(재처리 허용 여부).
- [K7] 하위 호출(계정계·카드사·외부 기관)까지 같은 거래 키를 전달해 끝단에서도 중복을 막는지 확인한다.
- [K8] 검증과 사후 탐지를 제시한다: 동시 중복 요청 테스트, 타임아웃 후 재시도 시나리오 테스트, 원장·거래 키 기준 중복 대사 쿼리.

## 흔한 실수와 반례
- 타임아웃이 나면 실패로 보고 같은 요청을 새로 보낸다 → 원 요청이 서버에서 이미 처리됐을 수 있어 이중 출금이 난다 → 거래 키로 처리 여부를 조회한 뒤 재시도하거나, 서버가 같은 키를 중복으로 판정하게 한다.
- "SELECT COUNT(*)로 없으면 INSERT"로 중복을 막는다 → 동시에 들어온 두 요청이 모두 0건을 보고 둘 다 처리한다 → 유일 제약을 두고 위반(Spring `DuplicateKeyException`)을 중복 응답으로 바꾼다.
- 멱등 키를 서버가 요청 수신 시 새로 생성한다 → 재시도마다 새 키가 생겨 중복 판정이 안 된다 → 키는 재시도해도 변하지 않도록 요청자가 만들어 함께 보낸다.
- 키만 같으면 무조건 이전 응답을 돌려준다 → 클라이언트 버그로 키를 재사용한 다른 금액 이체가 조용히 "성공"으로 응답된다 → 페이로드 지문을 비교해 불일치는 오류로 거절한다.
- 유일 키 컬럼을 NULL 허용으로 둔다 → 키가 비어 들어온 요청은 유일 제약을 항상 통과해 중복 방지가 무력화된다 → NOT NULL을 함께 걸고 키 누락 요청은 거절한다.
- 내 서버에서만 중복을 막고 하위 계정계 호출은 매번 새 거래번호로 보낸다 → 내 서버 재시도가 하위 시스템에서 이중 처리된다 → 같은 거래 키를 끝단까지 전달하고 하위 시스템의 중복 처리 규약을 확인한다.
- 멱등 처리 기록을 본 거래와 다른 트랜잭션에서 먼저 "완료"로 저장한다 → 본 거래가 롤백돼도 키는 완료로 남아 재시도가 막힌다 → 키 상태와 본 거래 반영의 원자성, 또는 처리 중 상태와 복구 절차를 함께 설계한다.

## 수준별 기대 답변
### 수준 2
- 로그나 데이터에서 같은 거래가 두 번 반영됐음을 확인하고 "타임아웃 후 재시도로 이중 처리됐다"까지 식별한다.
### 수준 3
- 재시도 주체와 경로를 특정하고, 멱등 키 + 유일 제약 + 상태 저장으로 막는 방안을 다른 대안(재시도 금지, 조회 후 재시도)과 비교한다.
- 이미 생긴 중복 건을 찾는 대사 쿼리와 동시 요청 테스트로 검증 방법을 제시한다.
### 수준 4
- 처리 중 서버 장애, 키 만료 이후 재요청, 하위 시스템까지의 키 전달, 키 저장소 장애처럼 여러 실패 시나리오에서 데이터가 어떤 상태로 남는지와 복구 절차를 설명한다.
- 재시도 정책(횟수·간격)과 멱등 설계를 함께 놓고 운영 비용(키 보관 기간, 저장 용량)까지 판단한다.

## 꼬리질문 후보
- 타임아웃이 났을 때 원 요청이 처리됐는지 어떻게 알 수 있나요?
- 멱등 키는 누가 만들어야 하나요? 서버가 만들면 왜 안 되죠?
- 같은 키로 금액이 다른 요청이 오면 어떻게 응답하겠어요?
- 첫 요청이 아직 처리 중일 때 같은 키로 재요청이 오면요?
- 키를 저장한 직후 본 거래 처리 전에 서버가 죽으면 그 키는 어떤 상태로 남나요? 재시도는 어떻게 되죠?
- 유일 제약 대신 분산 락을 쓰면 무엇이 다른가요?
- 멱등 키를 언제까지 보관하나요? 만료 후 같은 키가 오면요?
- 이미 운영에서 중복 처리된 건은 어떻게 찾아서 정리하겠어요?

## 시나리오 재료
- 모바일 이체 API에서 계정계 응답이 게이트웨이 timeout(예: 10초)을 넘겨 앱이 자동 재시도했고, 출금 원장에 같은 금액·같은 계좌가 2건 생긴 사례.
- 카드 승인 요청이 가맹점 단말 재전송으로 2번 들어와 승인 번호가 2개 발급된 사례.
- 보험금 지급 배치가 중간 실패 후 처음부터 재실행되어 일부 지급 건이 두 번 송금 요청된 사례.
- GA 채널 계약 등록 API를 외부 시스템이 응답 지연 때문에 재호출해 같은 계약이 2건 생성된 사례.
- 멱등 키 컬럼이 NULL 허용이라 구버전 앱 요청에서 중복 방지가 작동하지 않은 사례.
- 같은 멱등 키로 금액만 다른 이체 요청이 들어왔는데 서버가 이전 성공 응답을 그대로 돌려준 사례.
- 메시지 큐 at-least-once 재전달로 포인트 적립 이벤트가 2번 처리된 사례.
- 이중 처리 의심 건을 찾기 위해 거래 키·계좌·금액·시각 기준 대사 쿼리를 설계해야 하는 사례.
