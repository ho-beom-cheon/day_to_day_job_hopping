## 핵심 개념
- Oracle 옵티마이저는 인덱스 선두 컬럼이 조건(`=`, `<`, `>` 등)에 있을 때 index range scan을 고려한다. 선두 컬럼이 조건에 없으면 range scan 대신 index skip scan을 고려할 수 있으며, skip scan은 선두 컬럼의 고유값이 적을 때 효율적이다.
- 인덱스는 컬럼 값 자체를 저장한다. 함수 기반 인덱스가 아니라면 인덱스 컬럼에 함수를 씌운 조건(`TO_CHAR(reg_dt,'YYYYMMDD') = :d`)이나 암묵적 형변환(문자 컬럼을 숫자와 비교해 `TO_NUMBER`가 적용되는 경우)은 그 인덱스를 쓰지 못하게 한다. `LIKE '%abc'`처럼 앞에 와일드카드가 오면 range scan 대상이 아니다.
- 테이블 블록 대부분을 읽어야 하는 비선택적 조건이면 인덱스가 있어도 full table scan이 선택된다. 통계가 오래됐거나 힌트·병렬도 설정도 접근 경로에 영향을 준다. full scan이 항상 나쁜 것은 아니다.
- cardinality는 각 단계가 반환하는 행 수 추정치이고 실행 계획 전체에 영향을 준다. cost는 추정 자원 사용량일 뿐 시간과 같지 않으며 서로 다른 쿼리의 cost끼리 비교할 수 없다.
- `EXPLAIN PLAN`은 실행 환경과 달라 실제 계획과 다를 수 있다(스키마, 통계, 바인드 변수 값·타입, 세션 파라미터 차이). 실제 사용된 계획은 커서 캐시의 계획을 보여 주는 `DBMS_XPLAN.DISPLAY_CURSOR`나 `V$SQL_PLAN`으로 확인한다.
- MyBatis `#{}`는 PreparedStatement 바인드 파라미터로, `${}`는 문자열 그대로 SQL에 끼워 넣는다. `${}`에 사용자 입력을 그대로 넣으면 안전하지 않다. 동적 SQL(`<if>`, `<choose>`, `<where>`, `<foreach>`)은 입력에 따라 SQL 문장 자체가 달라지므로, 조건 조합마다 실행 계획을 따로 봐야 한다.

## 판단 기준
- [K1] 느린 SQL에서 실제 실행 계획을 확보한다. 추정 계획(EXPLAIN PLAN)과 실제 계획(DISPLAY_CURSOR)을 구분하고, 운영과 같은 바인드 조건으로 확인한다.
- [K2] 실행 계획에서 접근 경로(full scan, range scan, skip scan)와 추정 행 수를 읽어 병목 단계를 특정한다.
- [K3] 인덱스를 못 쓰게 만드는 조건 형태를 찾는다: 컬럼 가공 함수, 암묵적 형변환, 선두 와일드카드 LIKE, 선두 컬럼 누락.
- [K4] 복합 인덱스 컬럼 순서를 조회 패턴(등호 조건, 범위 조건, 정렬)과 선택도로 정하고 근거를 댄다.
- [K5] 인덱스 추가 비용을 함께 따진다: DML(INSERT·UPDATE) 부하, 저장 공간, 기존 실행 계획 변경 위험.
- [K6] MyBatis 동적 SQL이 만드는 조건 조합별 SQL을 펼쳐 보고, 자주 쓰이는 조합마다 계획을 확인한다. 조건이 모두 빠진 경우의 전체 조회 위험도 확인한다.
- [K7] `${}` 사용처(정렬 컬럼, 테이블명)를 찾아 허용 목록으로 제한하고, 값은 `#{}` 바인드로 바꾼다.
- [K8] 개선 효과를 같은 조건에서 전후 비교로 검증한다: 실행 계획, 읽은 블록·처리 행 수, 응답 시간, 데이터 분포가 다른 바인드 값.

## 흔한 실수와 반례
- `EXPLAIN PLAN` 결과만 보고 "인덱스를 탄다"고 결론 낸다 → 바인드 변수·통계·세션 차이로 실제 계획이 다를 수 있다 → 실행된 커서의 계획을 `DISPLAY_CURSOR`로 확인한다.
- cost가 낮아졌으니 빨라졌다고 보고한다 → cost는 시간이 아니고 다른 쿼리끼리 비교할 수 없다 → 같은 조건의 실제 응답 시간·처리 행 수로 비교한다.
- 날짜 검색을 `TO_CHAR(REG_DT,'YYYYMMDD') = #{date}`로 쓴다 → 컬럼 가공으로 REG_DT 인덱스를 못 쓴다 → `REG_DT >= :d AND REG_DT < :d + 1` 같은 범위 조건으로 바꾸거나, 가공이 꼭 필요하면 함수 기반 인덱스를 검토한다.
- VARCHAR2 고객번호 컬럼에 숫자 타입 파라미터를 바인드한다 → 컬럼 쪽에 형변환이 적용되면 인덱스를 못 쓴다 → 파라미터 타입을 컬럼 타입과 맞춘다.
- 조회가 느리면 조건 컬럼마다 단일 인덱스를 추가한다 → DML 비용이 늘고 다른 쿼리 계획이 바뀔 수 있으며, 결합 조건에는 복합 인덱스가 더 맞을 수 있다 → 조회 패턴 기준으로 복합 인덱스를 설계하고 영향받는 SQL을 확인한다.
- 인덱스만 있으면 항상 빠르다고 본다 → 대부분 행을 읽는 조건이면 full table scan이 더 싸다 → 선택도를 보고 판단한다.
- 정렬 컬럼을 `ORDER BY ${sort}`로 화면 입력에서 바로 받는다 → 문자열이 그대로 들어가 SQL 주입 위험이 있다 → 허용 컬럼 목록에 매핑한 값만 넣는다.

## 수준별 기대 답변
### 수준 2
- 실행 계획에서 full table scan이나 비효율 단계를 찾고 "REG_DT에 함수를 씌워 인덱스를 못 탑니다"처럼 원인 하나를 식별한다.
### 수준 3
- 실제 계획 확보 → 병목 단계 특정 → 원인(조건 형태·인덱스 구조·통계) → 수정안 비교(SQL 수정, 인덱스 추가·변경) → 전후 비교 검증 순으로 설명한다.
- MyBatis 동적 SQL의 주요 조건 조합별로 계획을 확인해야 함을 안다.
### 수준 4
- 데이터 분포가 치우친 경우, 인덱스 추가가 다른 배치·DML에 주는 영향, 운영 반영 절차(반영 시간대, 계획 변경 감시, 되돌리기)까지 판단한다.
- "왜 그 컬럼 순서죠?", "그 인덱스 때문에 야간 배치가 느려지면?" 같은 꼬리질문에 근거로 답한다.

## 꼬리질문 후보
- EXPLAIN PLAN과 실제 실행 계획이 다를 수 있는 이유는 무엇인가요?
- 복합 인덱스 (A, B) 순서를 (B, A)로 바꾸면 이 쿼리와 다른 쿼리에 어떤 영향이 있나요?
- 인덱스가 있는데 옵티마이저가 full scan을 고르는 건 언제 맞는 선택인가요?
- cost가 1/10로 줄었는데 응답 시간은 그대로입니다. 왜 그럴 수 있죠?
- MyBatis `<if>` 조건이 다섯 개면 실행 계획은 몇 개를 확인하겠어요? 전부 다 보나요?
- 인덱스를 추가했을 때 INSERT가 많은 테이블이면 무엇을 확인하겠어요?
- 운영에서만 느리고 개발에서는 빠릅니다. 무엇부터 비교하겠어요?
- `${}`를 꼭 써야 하는 경우는 언제이고 어떻게 안전하게 쓰나요?

## 시나리오 재료
- 기업 여신 심사 화면의 기업 현황 검색이 특정 조건 조합(기간만 입력)에서만 수십 초 걸리는 사례. MyBatis `<if>` 조건 5개.
- 카드 거래내역 조회에서 `TO_CHAR(APPR_DT,'YYYYMMDD') BETWEEN` 조건 때문에 승인일자 인덱스를 못 쓰는 사례.
- VARCHAR2 고객번호 컬럼에 숫자 바인드가 들어가 인덱스를 못 타는 신용정보 조회 API 사례.
- 보험 계약 테이블에 (상품코드, 계약일자) 인덱스가 있는데 계약일자만으로 조회해 skip scan 또는 full scan이 나오는 사례.
- 개발 DB에서는 0.2초인 조회가 운영에서는 15초 걸리고, EXPLAIN PLAN은 두 환경이 같게 나오는 사례.
- 조회 성능을 위해 인덱스 3개를 추가했더니 야간 거래 적재 배치 시간이 늘어난 사례.
- 화면 정렬 기능이 `ORDER BY ${sortColumn} ${sortDir}`로 구현돼 있는 코드 리뷰 사례.
- 고객명 부분 검색이 `LIKE '%' || #{name} || '%'`로 구현된 사례와 요구사항 조정 여부 판단.
